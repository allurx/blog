一个线程接收待处理图片，另一个线程负责压缩。没有图片时，压缩线程可以等待；处理不过来时，接收线程则需要决定继续等待，还是拒绝这次提交。`BlockingQueue` 把线程之间的交接和等待放进同一套接口，生产者不必自己反复检查队列，消费者也不必循环询问“有任务了吗”。

选接口时，最有用的问题是：这一步暂时做不到，调用者希望发生什么？回答之后，再决定队列容量和结束协议。

本文按 Java SE 25 的 BlockingQueue API 说明。基础队头语义见 [Queue](/queue/)；可直接运行的有限生产消费程序在 [LinkedBlockingQueue](/linked-blocking-queue/#用有限任务观察生产与消费)。

## 一次交接有四种等待方式

| 操作 | 异常形式 | 立即返回特殊值 | 等待条件满足 | 最多等待给定时间 |
| --- | --- | --- | --- | --- |
| 插入 | add | offer | put | offer(timeout) |
| 移除队头 | remove | poll | take | poll(timeout) |
| 查看队头 | element | peek | 无此接口 | 无此接口 |

有界队列已满时，put 等待容量或响应中断；take 在空队列上等待元素或响应中断。带超时 offer 失败返回 false，带超时 poll 失败返回 null。超时指定等待预算，不保证线程准点获得 CPU。

异常与特殊值的区别只针对相应失败条件。BlockingQueue 禁止 null 元素，插入 null 仍会失败；接口也不保证所有实现都有相同容量。无界实现的 put 通常不会因为业务容量上限等待，但仍受实际内存限制。

## 让图片处理队列有明确的容量和寿命

### 队列满了，由谁等待

假设压缩线程每秒处理 10 张图片，接收端却持续每秒送来 20 张。无界队列每秒就会多积压约 10 个任务；即使还能分配内存，后面的图片也会越等越久。有界队列把这个问题暴露在提交时：`put` 让生产者等待，`offer` 允许立即拒绝，限时 `offer` 则给等待设一个预算。

remainingCapacity 只是查询时刻的值。先检查它再 put/offer 之间，其他线程可能改变容量；是否成功应以实际操作结果为准，不能用查询构造一个没有同步保护的保证。

### 任务处理完以后怎样结束

队列暂时为空，与以后不会再有任务，是两件不同的事。`BlockingQueue` 没有统一的 `close` 方法；消费者若一直调用 `take`，最后一个任务处理完后仍会等待。调用者需要定义有限任务数量、结束标记或外部取消，并明确由谁等待线程退出。

在只有一个生产者、一个消费者的图片例子里，可以由生产者在最后一张图片之后放入结束标记。增加消费者后，一个消费者取走标记并不会自动通知其他消费者，关闭协议也必须随之调整。等待操作抛出 `InterruptedException` 时，应按这套协议退出或向上报告，不能无条件继续等待。

## 交接元素时，哪些状态受到保证

### 放入前的写入对消费者可见

线程在放入元素之前的动作，happens-before 另一个线程随后访问或移除该元素之后的动作。因此消费者能够看到交接前已发布的状态。

这不意味着生产者可以在放入后继续无同步地修改同一个可变对象。后续修改仍需要自己的同步协议；最容易理解的交接方式通常是不可变消息，或明确转移对象所有权。

例如生产者先给任务设置图片路径，再调用 `put`，消费者在 `take` 之后能看到这个路径。若生产者放入之后又修改任务的压缩参数，这次后续写入就不由先前的入队动作保证可见。不可变任务对象可以让交接关系更容易理解。

### 批量转移可能只完成一部分

drainTo 把当前可移出的元素加入目标集合；目标 add 抛异常时，元素可能已经部分转移，接口不提供通用事务回滚。目标集合也必须满足自己的并发要求。remove(Object)、contains 等查询与删除还要遵守具体实现对参数的约束。

需要进一步看等待怎样实现，可以继续阅读 [LinkedBlockingQueue](/linked-blocking-queue/)：容量计数决定能否交接，两把锁保护队列两端，条件变量负责让暂时不能继续的线程等待。
