x86 常被称为“强内存模型”，但强并不等于顺序一致。两个核心各自先写一个变量，再读取对方写的变量时，两个读取仍可能同时得到旧值。站在每个核心内部看，指令顺序没有消失；差异出在 Store 可以先进入本地缓冲，而后面的 Load 已经从共享内存取得结果。

本文用经典的 Store Buffering litmus test 建立这条因果链，再说明 x86-TSO 保证了什么、放松了什么，以及 Fence 为什么能排除这种结果。讨论范围是普通、对齐的 write-back 内存访问，不包含 non-temporal Store、MMIO、页表更新和混合宽度访问；高级语言还要先满足自身的并发内存模型。

## 顺序一致性不允许两个读取都得到 0

假设 `x = 0`、`y = 0`，两个处理器执行以下机器级操作。`r0` 和 `r1` 是各处理器自己的寄存器：

```text
Processor 0                 Processor 1
MOV [x], 1                  MOV [y], 1
MOV r0, [y]                 MOV r1, [x]
```

如果所有内存操作都能排进一个全局序列，并且每个处理器的程序顺序都被保留，那么 `r0 = 0` 与 `r1 = 0` 不可能同时成立。

原因可以写成四条先后关系：

- Processor 0 的程序顺序要求 `Wx < Ry`。
- `Ry` 读到初始值 0，要求 `Ry < Wy`。
- Processor 1 的程序顺序要求 `Wy < Rx`。
- `Rx` 读到初始值 0，要求 `Rx < Wx`。

把它们首尾相接会得到：

$$
W_x < R_y < W_y < R_x < W_x
$$

严格的先后关系不可能形成环，所以顺序一致性必须排除这个结果。然而，Intel 体系结构允许较新的 Load 越过地址不同的较早 Store；Scott Owens、Susmit Sarkar 与 Peter Sewell 的 [x86-TSO 形式化模型](https://www.cl.cam.ac.uk/~pes20/weakmemory/x86tso-paper.tphols.pdf)也把上述 `r0 = 0 ∧ r1 = 0` 列为允许行为。

这里的“重排”描述的是其他处理器能够观察到的内存顺序，并不要求处理器真的把两条指令在流水线里颠倒执行。不同微架构可以采用不同实现，只要对软件暴露的结果符合体系结构内存模型即可。

## 每个处理器的 FIFO Store Buffer 足以解释结果

x86-TSO 可以用一个简化的抽象机理解：所有处理器共享一份内存，每个处理器另有一个先进先出的 Store Buffer。普通 Store 先追加到本地缓冲，处理器随后可以继续执行；缓冲中的条目稍后才按顺序写入共享内存。

上面的执行可以这样发生：

| 步骤 | Processor 0                                  | Processor 1                                  | 共享内存       |
| ---- | -------------------------------------------- | -------------------------------------------- | -------------- |
| 1    | 把 `x = 1` 放入自己的 Store Buffer         |                                              | `x=0, y=0`     |
| 2    |                                              | 把 `y = 1` 放入自己的 Store Buffer         | `x=0, y=0`     |
| 3    | 缓冲里没有 `y`，从共享内存读取 `y`，得到 0 |                                              | `x=0, y=0`     |
| 4    |                                              | 缓冲里没有 `x`，从共享内存读取 `x`，得到 0 | `x=0, y=0`     |
| 5    | 缓冲中的 `x = 1` 写入共享内存               | 缓冲中的 `y = 1` 写入共享内存               | `x=1, y=1`     |

关键不是 Store 被丢弃，而是它对其他处理器的可见时间被推迟。两个 Load 执行时，对方的 Store 都还没有离开对方的缓冲，所以都能读到共享内存中的初始值。

Store Buffer 解决了一个现实的性能问题。核心取得一条缓存行的写权限可能要等待一致性消息往返；如果每次 Store 都阻塞流水线直到写入对其他核心可见，延迟会直接落在执行路径上。先记录待提交的 Store，可以让核心在等待期间继续处理后续工作。

这个模型是程序员可用的体系结构抽象，不是对某款处理器内部电路的完整复刻。真实核心还会有乱序执行、Load Queue、Store Queue、推测执行和缓存一致性状态机。x86-TSO 的价值在于把这些细节收敛成一组可推理的可见行为。

## 同一地址的读取不会忘记自己的写入

如果 Load 访问的就是本处理器尚未提交的地址，直接读取共享内存会得到过期值：

```text
MOV [x], 1
MOV r0, [x]
```

x86-TSO 要求第二条指令得到 1。抽象模型让 Load 先搜索本处理器的 Store Buffer；若存在相同地址的待提交写入，就从最新的那一条转发结果。只有找不到同地址条目时，Load 才读取共享内存。

因此，Store→Load 放松有两个重要限定：

1. 较早 Store 与较晚 Load 访问不同地址时，Load 才可能先观察到共享内存状态。
2. 同一处理器仍能通过 Store-to-Load forwarding 立即读到自己的最新写入。

这也解释了一个容易混淆的现象：Processor 0 可以已经“知道”自己写入了 `x = 1`，同时 Processor 1 仍从共享内存读到 `x = 0`。本地可读取与全局可见是两个不同时间点。

## TSO 的 Total 约束的是 Store 顺序

Total Store Order 里的 `Total` 不能理解为“所有 Load 和 Store 都有单一总顺序”。它强调普通 Store 最终进入共享内存时具有统一顺序，而且每个处理器的 Store Buffer 是 FIFO。一个处理器先写 `x` 再写 `y`，两个写入不会以 `y`、`x` 的顺序对其他处理器可见。

对于本文范围内的普通 write-back 内存访问，可以用下表概括 x86 的基本顺序：

| 程序顺序中的操作对 | 是否允许后者越过前者 | 直观含义                               |
| ------------------ | -------------------- | -------------------------------------- |
| Load → Load        | 不允许               | 两次普通读取保持顺序                   |
| Load → Store       | 不允许               | 较新的写入不能越过较早读取             |
| Store → Store      | 不允许               | Store 按程序顺序对外可见               |
| Store → Load       | 不同地址时允许       | Load 可在较早 Store 全局可见之前完成   |

[Intel 64 and IA-32 Software Developer’s Manual, Volume 3](https://www.intel.com/content/dam/www/public/us/en/documents/manuals/64-ia-32-architectures-software-developer-system-programming-manual-325384.pdf)在多处理器内存排序章节中给出了这些基本原则和 litmus test。x86-TSO 论文进一步把它们收束为带本地写缓冲的操作模型，以及与之等价的公理化模型。

Store Buffering 的两个 Store 最终仍有一个全局顺序。假设 `Wx` 先写入共享内存，再轮到 `Wy`，这个顺序与两个 Load 先前读到什么并不矛盾：读取发生时，两个 Store 都还可以停留在各自缓冲中；缓冲稍后排空时才形成全局可见顺序。

## MFENCE 排除的是延迟可见窗口

若在每个处理器的 Store 和 Load 之间加入完整内存屏障：

```text
Processor 0                 Processor 1
MOV [x], 1                  MOV [y], 1
MFENCE                      MFENCE
MOV r0, [y]                 MOV r1, [x]
```

`MFENCE` 要求屏障前的内存访问先于屏障后的内存访问对外完成。套用 Store Buffer 抽象，可以把它理解为后面的 Load 不能在前面的 Store 尚未满足顺序要求时越过去。

现在假设 Processor 0 先越过自己的 `MFENCE`。它的 `x = 1` 已经对其他处理器可见；若 Processor 1 此后读取 `x`，就不能再得到初始值 0。若 Processor 1 的读取发生得更早，那么它必然已经越过自己的 `MFENCE`，`y = 1` 也已经可见，Processor 0 随后的读取就不能得到 0。无论哪一侧先完成屏障，都至少有一次读取看到 1，所以 `r0 = 0 ∧ r1 = 0` 被排除。

Linux 内核的 [Store buffering 示例](https://docs.kernel.org/dev-tools/lkmm/docs/recipes.html#store-buffering)展示了同一个结构：两个 CPU 都是先 Store 后 Load，只有两侧都使用完整屏障，才能禁止两个读取同时得到旧值。少任意一侧的完整屏障，另一侧仍可能在必要顺序建立前完成读取。

实际程序不应见到跨线程可见性问题就机械插入 `MFENCE`。锁、原子读改写指令和语言级 acquire/release 或 sequentially consistent 操作往往能更准确地表达协议，也让编译器与不同处理器选择合适实现。Fence 只提供顺序，不自动创建互斥、重试、所有权或数据结构不变量。

## 强内存模型也不能替高级语言兜底

上面的 litmus test 使用机器级操作描述。把它原样翻译成 C 或 C++ 的普通变量，会形成数据竞争；C++ 不再承诺这些读取和写入具有本文分析的行为。编译器还可能在到达硬件之前重排、合并或删除访问。

Java 普通字段也不能仅凭“运行在 x86 上”建立跨线程通信。Java Memory Model 决定合法执行和 happens-before 关系，`volatile`、锁以及并发类才是相应的同步工具。硬件模型只约束编译后真正发出的机器访问，不会恢复高级语言没有提供的语义。

即使使用语言原子操作，也要区分目标。`relaxed` 原子可以消除 C++ 数据竞争，却不承诺跨地址的顺序；release/acquire 只有在读取观察到相应发布时才形成同步；顺序一致原子提供更强的全局约束。正确做法是先用语言模型证明协议，再检查编译器如何把所需顺序映射到 x86 指令，而不是从某次汇编输出反推源程序永远正确。

## 模型边界决定结论能否直接套用

“x86 只有 Store→Load 会放松”是一条便于入门的概括，但必须带上访问类型和内存属性。本文采用的 x86-TSO 模型面向典型用户代码和大部分内核代码中的 coherent write-back 内存，同时排除了若干会改变规则的情况：

- non-temporal Store 和 write-combining 内存具有不同的排序约束；
- MMIO 需要设备访问 API 与相应屏障，不能按普通缓存内存推理；
- 未对齐、跨缓存行或混合宽度访问还涉及原子性问题；
- 自修改代码、页表更新和异常处理需要额外的序列化规则；
- DMA 与非一致性设备还要处理 CPU、设备和总线之间的可见性。

这些边界不是对基本模型的否定。相反，先明确普通 write-back 内存下的强保证，才能知道何时已经离开这个模型，需要查阅指令、内存类型或设备接口的专门规则。

x86-TSO 的核心取舍可以归结为一句话：Store 保持彼此的全局顺序，但允许较晚的、不同地址的 Load 在较早 Store 尚未全局可见时完成。FIFO Store Buffer 让核心隐藏写入延迟，Store-to-Load forwarding 保住单线程直觉，完整 Fence 则在协议真正需要时关闭这段可见性窗口。理解这三者后，“x86 很强”与“两个核心仍能同时读到 0”就不再矛盾。
