停止应用线程后再遍历对象图，垃圾收集器看到的是一幅静止的图。若标记线程与应用线程并发运行，应用可能在遍历期间改写引用：一个仍被根引用的对象，可能恰好从收集器尚未检查的边上移到已经检查过的对象下面。只让收集器继续扫描，可能永远看不到这条新路径。

写屏障（write barrier）是在引用写入前后附加的一小段运行时逻辑。它不是禁止应用修改对象，而是把可能破坏标记正确性的信息补交给收集器。理解它需要的前提只有可达性遍历和对象引用；本文用三色模型构造一次漏标，再比较增量更新与 snapshot-at-the-beginning（SATB）如何修复。

## 三种颜色记录遍历进度

标记阶段可以把对象的逻辑状态分成三类：

| 颜色 | 含义 |
| --- | --- |
| 白色 | 尚未被发现，本轮结束时仍为白色才可作为垃圾回收 |
| 灰色 | 已知可达，但它的引用字段还没有全部扫描 |
| 黑色 | 已知可达，而且它的引用字段已经扫描完毕 |

开始时根直接指向的对象被染成灰色，其余对象为白色。收集器反复取出一个灰色对象，把它指向的白色对象染灰，再把自己染黑。没有灰色对象时遍历结束；在对象图不变化的前提下，黑色对象不会指向白色对象，剩余白色对象也就不可达。

[Dijkstra 等人的并发垃圾收集论文](https://www.cs.utexas.edu/~EWD/transcriptions/EWD05xx/EWD520.html)用颜色描述标记，并把“黑色节点不能指向白色节点”写成标记期间需要维护的不变量。三色不是对象头必须存储的三个枚举值，而是对遍历状态的抽象；具体实现可以用位图、队列和其他状态编码它们。

## 两次引用写入足以藏起一个活对象

考虑根同时指向 `A` 和 `C`，而 `A.child` 指向 `B`。收集器已经扫描完 `C`，但还没扫描 `A`，此时颜色如下：

```text
root ──► A(灰) ──► B(白)
  └────► C(黑)
```

应用线程接着执行两次写入：

```java
C.child = B;
A.child = null;
```

第一步建立了黑色 `C` 到白色 `B` 的引用；第二步在收集器扫描 `A` 前移除了旧路径。之后收集器查看 `A` 时已经找不到 `B`，而 `C` 又不会被重复扫描。灰色集合最终为空，`B` 仍能由根经过 `C` 到达，却保持白色。如果回收器按颜色释放它，就会把活对象误判为垃圾。

漏标需要两件事同时发生：黑色对象获得指向白色对象的引用，并且通往该白色对象的其他、尚可被收集器发现的路径被删除。写屏障只要破坏这个组合，就能恢复安全性。常见方案选择保护新边或保护旧边。

## 增量更新补记新引用

增量更新（incremental update）关注写入产生的新边。概念上的屏障可以写成：

```text
写入 x.field = newValue 时：
    若 x 已是黑色且 newValue 仍为白色：
        将 newValue 染成灰色
    完成引用写入
```

在前面的例子里，执行 `C.child = B` 时，屏障把 `B` 放回待扫描集合。即使 `A.child` 随后被清空，收集器仍会访问 `B`。有的实现不直接标记目标，而是把来源对象重新变灰；两者都让新增引用重新进入遍历范围。

这种方案维持的是更新后的对象图：应用新建一条可能藏起白色对象的边时，收集器追上变化。屏障不一定真的逐次操作全局队列；实际运行时通常先写入线程本地缓冲区，并为无需记录的常见情况保留很短的快速路径。

## SATB 在删除旧引用前留下线索

SATB 选择另一条不变量：标记应覆盖本轮开始瞬间可达的对象。应用准备覆盖引用时，预写屏障先取得旧值：

```text
写入 x.field = newValue 前：
    oldValue = x.field
    若并发标记正在进行且 oldValue 需要记录：
        将 oldValue 加入 SATB 队列
    完成引用写入
```

在例子中，`A.child = null` 会先记录旧值 `B`，所以旧路径虽然从当前对象图消失，收集器仍能发现 `B`。[Yuasa 的实时垃圾收集论文](https://www.yuasa.kuis.kyoto-u.ac.jp/~yuasa/YuasasSnapshot.pdf)提出了这种在覆盖指针时保存旧引用的做法；它后来通常被称为 snapshot-at-the-beginning。

这里的“快照”是标记所需的可达性语义，不是复制一份字节完全不变的堆。对象字段仍可继续变化。一个对象若在本轮开始时可达、随后变成垃圾，SATB 仍可能保留它到下一轮，这类对象称为浮动垃圾。多保留一轮是可接受的保守结果，漏掉仍存活的对象则不安全。

增量更新与 SATB 可以用同一组变化对照：

| 策略 | 屏障保留的信息 | 前述例子中的触发写入 | 典型取舍 |
| --- | --- | --- | --- |
| 增量更新 | 新引用指向的对象，或需要重扫的来源对象 | `C.child = B` | 跟进标记开始后的新边，可能需要重扫 |
| SATB | 被覆盖的旧引用 | `A.child = null` | 保留开始时的可达性，允许产生浮动垃圾 |

“预写”和“后写”描述屏障相对引用存储发生的时机，不是相对整轮 GC 的先后。SATB 必须在旧值消失前观察它，因此自然使用预写屏障；保护新边的屏障则观察新值或被改写的对象。

## HotSpot G1 同时有两种用途不同的写屏障

OpenJDK 当前主线中的 G1 是 SATB 的具体实现例子，不代表所有收集器都采用相同方案。[`G1BarrierSet`](https://github.com/openjdk/jdk/blob/master/src/hotspot/share/gc/g1/g1BarrierSet.hpp)同时声明了 `write_ref_field_pre`、`write_ref_field_post` 和 SATB 标记队列。以 x86 实现为例，[预写屏障的汇编生成代码](https://github.com/openjdk/jdk/blob/master/src/hotspot/cpu/x86/gc/g1/g1BarrierSetAssembler_x86.cpp)会先检查 SATB 标记是否活跃，读取非空旧引用，并优先把它写入当前线程的缓冲区；缓冲区满时才进入运行时慢路径。

同一份源码还在实际存储之后调用 G1 的后写屏障，将相关 card 标脏。这个后写屏障主要服务于记忆集：区域化、分代收集不能每次扫描整个堆，需要记录可能包含跨区域引用的内存片段。它与 SATB 预写屏障出现在同一次引用赋值附近，但解决的问题不同：前者帮助局部收集找到区域间引用，后者防止并发标记漏掉旧路径。不能因为都叫 write barrier，就把 card marking 当成 SATB 的另一种写法。

源码中的缓冲、空值过滤和活跃状态检查也说明，屏障是编译器与运行时共同实现的协议，而不是 Java 源码层可调用的 API。屏障会增加每次引用写入的成本；线程本地队列、批量处理和快速路径用于把常见写入的额外工作限制在较小范围内。

## 写屏障只修复对象图变化这一类问题

安全的并发回收器还需要处理写屏障之外的状态：

- 根和线程栈可能随应用执行变化，需要暂停点、握手或专门的根处理协议；
- 屏障缓冲区必须被可靠排空，收集器还要判断并发标记何时真正结束；
- 弱引用、终结机制和类卸载需要在标记结果上执行额外处理；
- 并发移动对象还涉及转发指针或读屏障，三色写屏障本身不能保证引用重定位正确；
- 屏障与标记线程之间仍须满足实现所需的原子性和内存顺序。

因此，“使用三色标记”并不会自动带来并发安全。三色只提供了描述问题的模型：应用线程可能让收集器错过活对象。增量更新记录新边，SATB 记录即将消失的旧边，两者分别破坏漏标所需的条件。选定不变量之后，预写或后写屏障、缓冲区与重新扫描策略才有明确的设计依据。
