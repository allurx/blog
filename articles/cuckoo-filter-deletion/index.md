标准 Bloom Filter 把一个元素映射到多个共享位。清除其中任何一位，都可能抹掉其他元素仍在使用的证据，所以它不能直接删除。Cuckoo Filter（布谷鸟过滤器）同样允许误判，也不保存完整键，却能删除已经插入的元素：它保存的是可逐个移除的短指纹，并把每个指纹限制在一对可互相推导的桶中。

本文只解释这条删除语义如何成立，以及它依赖的边界。读者需要知道哈希表以桶存放条目；不要求先了解 Cuckoo Hashing 的插入算法。这里的“能删除”有严格前提：调用方必须知道目标元素确实插入过，并正确处理重复插入和插入失败。它不意味着过滤器能精确识别任意元素。

## 从共享位改为独立的指纹条目

设 `fp(x)` 是元素 x 的 f 位指纹。Cuckoo Filter 由许多桶组成，每个桶有 b 个条目，每个条目保存一份指纹。它不保存 x 本身，因此查询仍然是近似的：不同元素可能具有相同指纹，最终得到一次 false positive。

元素 x 有两个候选桶：

$$
i_1=h(x),
$$

$$
i_2=i_1\mathbin{\mathrm{xor}}h(fp(x)).
$$

插入成功后，一份 `fp(x)` 位于 `i₁` 或 `i₂`。查询重新计算指纹和两个桶，只要其中一个桶包含相同指纹，就回答“可能存在”；两个桶都没有，才回答“确定不存在”。

这与位数组有一个决定性的差别。Bloom Filter 的一个位可能同时是很多元素证据的一部分，却没有记录每个元素贡献了几次；Cuckoo Filter 的每次成功插入会占用一个完整条目。删除可以移除一份指纹，而不是修改一份无法区分归属的共享状态。关于标准 Bloom Filter 为什么不能清位，可对照[《Bloom Filter 的误判率从哪里来》](/bloom-filter-error-rate/)。

不过，只有“独立条目”还不够。若两个不同元素碰巧具有相同指纹，删除时仍无法判断某个条目最初属于谁。Cuckoo Filter 还需要保证：同一指纹若出现在同一个候选桶中，它对应的另一个候选桶也相同。

## 异或让两个候选桶可以往返

候选桶公式的关键是异或的自反性质。若指纹 f 当前位于桶 i，它的另一个桶可以只用当前桶号和指纹算出：

$$
j=i\mathbin{\mathrm{xor}}h(f).
$$

再算一次就会回到原桶：

$$
j\mathbin{\mathrm{xor}}h(f)
=i\mathbin{\mathrm{xor}}h(f)\mathbin{\mathrm{xor}}h(f)
=i.
$$

这项性质首先解决插入时的搬迁问题。两个候选桶都满时，算法可以踢出其中一个指纹，把新指纹放进空出的位置，再仅凭“被踢出的指纹 + 当前桶号”找到它的另一个桶。即使表中没有原始键，搬迁链也能继续。原始论文把这种做法称为 partial-key cuckoo hashing；它是在只保存指纹的前提下继续使用 Cuckoo Hashing 的核心技巧。[Pagh 与 Rodler 的 Cuckoo Hashing 原论文](https://www.rasmuspagh.net/papers/cuckoo-jour.pdf)则给出了完整键场景下的双位置与搬迁基础。

同一公式也使删除在指纹碰撞下保持一致。假设 x 和 y 不同，却具有相同指纹 f，并且查询时都命中桶 i。因为另一个桶都由 `i xor h(f)` 得到，它们共享同一对候选桶。若 x、y 都成功插入，表中就应有两份 f；删除 x 时无论移除的是哪一份，仍有一份 f 留在这对桶中，y 的查询仍会命中。

可以把这一过程压缩成一张状态表：

| 状态 | 候选桶中的 f 数量 | 查询 x | 查询 y |
| --- | ---: | --- | --- |
| x、y 都已插入 | 2 | 可能存在 | 可能存在 |
| 删除 x 后 | 1 | 仍可能误判为存在 | 可能存在 |
| 再删除 y 后 | 0 | 确定不存在 | 确定不存在 |

删除 x 后仍可能把 x 回答为“存在”并非删除失败。过滤器只保留指纹，剩余的 y 正是 x 的碰撞来源；近似成员查询本来就允许这种阳性误判。重要的是，删除一份已插入记录不会让另一份已插入记录变成阴性。

[Fan、Andersen、Kaminsky 与 Mitzenmacher 的 Cuckoo Filter 论文](https://www.cs.cmu.edu/~dga/papers/cuckoo-conext2014.pdf)给出的删除算法因此很短：计算 f、`i₁` 和 `i₂`，在两个桶中找到一份 f 并移除。无需沿搬迁链反向查找，也无需移动其他条目填洞。

## 指纹越短，误判越多

一次阴性查询最多比较两个桶中的 `2b` 个指纹。把每个 f 位指纹视为均匀值，一次比较碰撞的概率至多为 `1 / 2^f`。若暂按独立比较估算，误判概率的上界为：

$$
\varepsilon
\le 1-\left(1-\frac{1}{2^f}\right)^{2b}
\approx\frac{2b}{2^f}.
$$

因此，为了把目标误判率控制在 ε 附近，原论文给出如下指纹长度近似：

$$
f\ge\left\lceil\log_2\frac{2b}{\varepsilon}\right\rceil.
$$

例如每桶 4 个条目、目标误判率 1%，代入得到 `ceil(log₂(800)) = 10` 位。这个数值说明参数之间的关系，不是任意实现都能无条件兑现的服务承诺。真实误判率还受装载率、哈希质量、指纹编码和查询分布影响；面对攻击者可控输入时，均匀随机模型更不能替代安全分析。

桶变大可以提高表的可装载程度，却也让每次查询比较更多指纹，需要更长指纹维持同样误判率。存储成本同样包含空位：若装载率为 α，每个指纹 f 位，则平均每个已插入元素约占 `f / α` 位。参数选择是在装载率、误判率、查询局部性和插入失败风险之间取舍，不能只盯着指纹长度。

## 删除非成员会把误判变成漏判

Cuckoo Filter 最容易被误用的接口是 `delete(x)`。若 x 从未插入，查询 x 仍可能因为另一个元素 y 的指纹碰撞而回答“可能存在”。此时按相同规则删除一份匹配指纹，就会真的移除 y 的记录。之后查询 y 可能返回“确定不存在”，产生 false negative。

所以删除前不能用过滤器自身的阳性回答证明“x 确实插入过”。这是一段循环论证：近似查询只能证明两个桶里有相同指纹，无法证明原始键相同。安全的删除必须由过滤器之外的事实支撑，例如权威集合已经确认该键存在，或者业务协议保证删除请求只对应成功插入且尚未删除的记录。

这个边界也解释了为什么删除 API 的布尔返回值很弱。返回 `true` 最多表示“找到并移除了一份相同指纹”，不能证明被移除的就是 x 的身份记录。若业务需要对任意删除请求做精确鉴权、幂等判断或审计，仍要保留精确集合或计数来源。

## 重复插入必须按次数成对删除

为了让前面的碰撞推理成立，支持删除的 Cuckoo Filter 不能随意合并重复指纹。每次成功插入都要保留一份条目，每次删除只移除一份。否则，同一键插入两次却只存一份，第一次删除就会让第二份逻辑记录消失。

这带来两个限制：

- 调用方要区分“集合语义”和“多重集合语义”。若业务只允许一个键存在一次，应在外部阻止重复插入；若允许引用计数，则插入、删除次数必须配对。
- 重复值会集中占用同一对桶。每桶 b 个条目时，这对桶总共只有 `2b` 个位置；继续插入同一键最终必然失败。增加总桶数也不会扩大这一个键的候选位置。

并发实现还需要让插入、搬迁和删除具有合适的同步语义。本文的结构推理假设每个操作观察到一致状态，且成功插入不会在搬迁失败时遗失被踢出的指纹。锁、版本号或原子更新方式属于具体实现契约，不能由数据结构名称自动保证。

## 插入失败是正常结果，不是可忽略异常

标准 Bloom Filter 可以持续置位，只是超过规划容量后误判率不断上升。Cuckoo Filter 有明确的放置约束：每个指纹只能进入两个桶。装载率升高后，搬迁可能在规定次数内找不到空位，插入会失败。

调用方若忽略失败并假装元素已经进入过滤器，之后的阴性查询就会漏掉真实成员。正确实现必须让失败对调用方可见，并选择扩容、重建、使用备用区或回退到权威存储。扩容也不能只把旧指纹随意复制到更多桶：第一候选桶来自完整键，而过滤器已经丢弃了完整键。具体库若支持自动扩容，必须核对它如何保存足够信息或分段组织过滤器。

原论文的实验配置在每桶 4 个条目时可达到约 95% 的高装载率，但这是特定算法、哈希和实验条件下的结果，不是所有实现的硬保证。接近容量上限时，插入延迟的长尾和失败概率通常比平均查询成本更值得监控。

## 选择它时真正要确认的契约

Cuckoo Filter 适合“允许阳性误判、需要动态删除、阴性结果可以节省一次昂贵精确查询”的场景。它的删除能力来自三个同时成立的条件：每次插入保存一份可移除指纹；同一指纹在某个桶中总能导出同一备用桶；调用方只删除确实成功插入的逻辑记录。

落地前应从具体实现文档或源码确认指纹位数、桶大小、最大装载率、重复键语义、插入失败处理、扩容方式和并发保证。过滤器仍不是权威数据源：阳性结果需要回查真实集合，阴性结果只有在所有成功写入都被纳入、失败未被忽略、删除协议正确时才可信。删除让近似集合可以随业务状态演化，但并没有把它变成精确集合。
