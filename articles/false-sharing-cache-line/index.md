两个线程各自维护一个计数器，代码中没有锁，也没有同时修改同一个变量，吞吐量却可能随着并行度增加而下降。问题有时不在变量本身，而在它们恰好落入同一条缓存行：处理器的一致性协议按缓存行追踪数据，无法只转移其中某个字段的写权限。

这种现象称为**伪共享**（false sharing）。本文从一次缓存行所有权往返开始，区分伪共享、真正共享和普通缓存未命中，再说明怎样取得证据以及何时值得调整布局。理解主线不需要掌握某一种具体的一致性协议；文中的状态名称只用于描述“可共享读取”和“取得独占写权限”这类共同机制。

## 源代码中的两个变量可能是硬件眼中的一个单元

假设两个 8 字节计数器在内存中相邻，而目标处理器的缓存行是 64 字节。它们可能处在同一行中：

```text
缓存行 L：字节 0                                              63
          ┌──────────┬──────────┬──────────────────────────────┐
          │ counterA │ counterB │ 其他数据或未使用空间         │
          └──────────┴──────────┴──────────────────────────────┘
             CPU 0 写     CPU 1 写
```

缓存以行为单位填充，一致性目录或探测也围绕这条行工作。CPU 0 读取 `counterA` 时，通常会把包含两个计数器的整行带入自己的缓存；CPU 1 读取 `counterB` 也会得到同一行的副本。只读阶段可以并存，冲突从写入开始。

CPU 0 要修改 `counterA`，必须先取得缓存行 L 的写权限，使其他核心持有的副本失效。随后 CPU 1 修改 `counterB`，也要取得 L 的写权限，于是刚到 CPU 0 的有效副本又被撤销。两个核心交替更新时，发生的是整条缓存行的所有权往返：

| 步骤 | CPU 0                                  | CPU 1                                  | 缓存行结果             |
| ---- | -------------------------------------- | -------------------------------------- | ---------------------- |
| 1    | 读取 `counterA`                       | 读取 `counterB`                       | 两边都可持有只读副本   |
| 2    | 写 `counterA`，请求 L 的独占写权限    | L 的副本失效                           | L 归 CPU 0 修改        |
| 3    | L 的副本失效                          | 写 `counterB`，请求 L 的独占写权限    | L 转给 CPU 1 修改      |
| 4    | 再写 `counterA`，重新请求 L 的写权限  | L 的副本再次失效                       | 所有权继续来回移动     |

线程在程序语义上没有共享变量，硬件却看到同一条不断被修改的缓存行，因此得名“伪共享”。[Linux 内核的伪共享文档](https://docs.kernel.org/kernel-hacking/false-sharing.html)用同一行里的引用计数与只读名称字段说明了相同问题：一个字段频繁写入，会迫使其他 CPU 反复重取它们只读的字段。

## 原子操作保证正确性，却不能缩小一致性粒度

把两个计数器声明为原子变量，可以保证各自更新不被撕裂，并按所选内存序提供相应保证；它不会让处理器按 8 字节字段分别维护缓存一致性。两个原子对象仍可能位于同一缓存行，两个核心仍要为该行交替取得写权限。

这解释了一个容易误判的现象：结果完全正确、线程也没有等待同一把锁，性能仍可能出现类似争用的扩展瓶颈。瓶颈来自数据位置和写入流量，不一定能在锁竞争分析中看到。

伪共享还要与几种相近现象分开：

- 两个线程更新**同一个计数器**属于真正共享。即使把这个计数器单独放进一条缓存行，写权限仍要在核心之间移动；填充无法消除算法本身的共享。
- 多个线程只读同一条缓存行通常不会形成这种所有权乒乓。至少有一个参与者持续写入，才会反复使其他副本失效。
- 首次访问或容量不足导致的普通缓存未命中，不要求另一个核心正在写同一行。伪共享的特征是不同核心访问同一行的不同位置，并产生与写入相关的一致性流量。
- 两个字段地址相邻不等于它们必然同处一行。对象起始地址、对齐、数组步长、运行时布局和处理器缓存行大小共同决定实际结果。

[Intel 的优化手册](https://www.intel.com/content/www/us/en/developer/articles/technical/intel64-and-ia32-architectures-optimization.html)也将 false sharing 定义为不同线程使用的无关变量映射到同一缓存行，并指出修改数据在核心间共享会带来额外延迟。常见 x86-64 处理器以 64 字节为缓存行，但代码不应把这个数字当成所有架构、所有缓存层级和所有运行环境的通用契约。

## 先证明缓存行在往返，再修改布局

“多线程变慢”只能形成怀疑，不能单独证明伪共享。调度迁移、内存带宽、真正共享、NUMA 距离、锁竞争和工作量不均衡都可能产生相似曲线。有效诊断需要把三个证据连接起来：

1. **工作负载证据**：问题随写线程增加而出现，并且能够在固定输入、预热方式和线程放置条件下稳定复现。先确认比较的是相同工作量，而不是更高并行度顺便做了更多事。
2. **硬件事件证据**：在支持的平台上，用 `perf c2c`、VTune 等工具定位频繁发生 cache-to-cache 传输的缓存行。Linux 的报告中，local/remote HITM 一类指标表示加载命中了其他核心持有的已修改副本，是值得继续检查的信号；具体事件可用性和含义仍取决于处理器 PMU。
3. **布局证据**：把热点地址映射回结构体偏移或数组元素，确认由不同线程写入的字段确实落在同一行。原生程序可结合调试符号、`pahole`、反汇编和对象地址完成映射；托管运行时还要核对实际对象布局，而不是只按源码字段顺序猜测。

Linux 内核文档建议先用 `perf record/report/stat` 找到热点，再用 `perf c2c` 定位高争用缓存行，并用 `pahole` 对照成员偏移。这套顺序很重要：缓存行事件指出“哪一行在移动”，布局信息解释“这一行里哪些字段不该一起移动”。

最后应做受控对照。只改变字段布局或分片方式，保持算法、输入、线程数和测量方法一致；若一致性事件与耗时同时下降，因果链才比较完整。只看到填充后的某一次跑分更快，仍可能是频率、调度或内存位置变化造成的偶然结果。

## 分离热点写入比盲目填充更可靠

最直接的修复是让不同核心频繁写入的数据落到不同缓存行，但“在两个字段之间塞 56 字节”并不是通用答案。结构体起始地址可能没有按行对齐，编译器或运行时布局规则可能变化，数组中相邻对象也可能跨越边界。有效方案要同时控制起始对齐和元素步长，并在目标环境验证实际地址。

更重要的是先减少共享写入，再考虑空间布局：

- **按线程或按 CPU 分片**：每个执行单元更新自己的局部计数，读取总数时再汇总。写入热路径不再争抢同一行，代价是读取更复杂、结果可能只在汇总点一致。
- **批量合并**：先在局部累积，达到阈值后再更新全局状态。它没有消除共享，但降低了所有权转移频率；阈值决定实时性与吞吐量之间的取舍。
- **重排字段**：把大多只读的字段放在一起，把由不同线程写入的热点字段分开；同时写入、生命周期相同的数据则可以保留邻近性，继续利用空间局部性。
- **避免无意义写入**：值未变化时不要无条件写回。少一次写入，可能就少一次使其他核心副本失效的请求。

这些做法都有成本。填充和对齐会增大对象、数组与工作集，占用更多缓存和 TLB 项；分片会增加汇总逻辑和一致性边界；重排一个热点字段也可能把其他字段推到新的冲突位置。Linux 内核文档因此明确提醒，伪共享不总是值得修复，应在性能收益、复杂度和空间开销之间权衡。

伪共享的关键不在“两个变量是否同名或同一对象”，而在某段时间内哪些核心以什么方式访问同一条缓存行。源码展示字段，缓存一致性协议管理行；从字段视角切换到缓存行视角，才能解释为什么无锁、无数据竞争且结果正确的程序仍会因并行写入而互相拖慢。诊断时先取得硬件事件和布局证据，优化时优先减少热点共享写入，再用经过验证的对齐与分离处理剩余冲突。
