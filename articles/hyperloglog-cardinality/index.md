统计一天有多少独立访客，最直接的办法是把用户 ID 放进集合，最后读取集合大小。结果精确，但空间随不同 ID 的数量一起增长。面对跨月日志或分布式数据流，真正困难的往往不是扫描一次数据，而是保存全部去重依据。

HyperLogLog（HLL）选择保留一个固定大小的概率摘要。它不记住元素，只观察元素哈希值中罕见的比特模式，再由这些观察估算不同元素的数量。代价是结果存在统计误差，收益是单遍处理、固定空间，并且多个摘要可以直接合并。

本文从“连续出现多少个 0”推导经典 HyperLogLog 的寄存器和估算公式。这里的基数是数据流中**不同值的数量**；重复值出现多少次不增加基数。

## 罕见模式暴露了样本规模

先假设哈希函数把不同输入均匀地映射为独立随机比特串。定义 `ρ(w)` 为比特串 w 中第一个 `1` 的位置，从 1 开始计数：

| 比特前缀 | `ρ(w)` |
| --- | ---: |
| `1...` | 1 |
| `01...` | 2 |
| `001...` | 3 |
| `0001...` | 4 |

要满足 `ρ(w) ≥ k`，开头必须至少有 k−1 个 0，因此：

$$
P(\rho(w) \ge k)=2^{-(k-1)}.
$$

`0001...` 这样的前缀平均每 8 个随机哈希才出现一次，十个前导零则大约每 1024 个出现一次。观察到越长的连续 0，通常意味着已经看过越多不同哈希。因此，如果一批数据中最大的 `ρ` 为 R，`2^R` 会落在基数所在的数量级附近。

这一步依赖的是**不同值经过均匀哈希后的样本数**。同一个值无论重复多少次都会产生相同哈希，也就重复同一条观察，不会伪装成更多样本。

只保存一个最大值仍然很不稳定。一次格外罕见的哈希就可能把估计放大许多倍；没有碰到罕见值时又会低估。HyperLogLog 的关键改进，是并行维持很多个小实验，再稳健地合并结果。

## 前 p 位分桶，剩余位测量

选择 `m = 2^p` 个寄存器，初始值都为 0。每个输入先计算固定宽度哈希：

1. 取前 p 位作为桶编号 j。
2. 在剩余位中计算 `ρ(w)`。
3. 将寄存器更新为 `M[j] = max(M[j], ρ(w))`。

桶编号把数据近似均匀地分成 m 条子流。每个寄存器只记录所属子流见过的最大 `ρ`，所以摘要大小不随输入数量增长。重复输入落到同一桶并得到同一个 `ρ`，再次执行 `max` 不会改变状态。

经典估算式为：

$$
E=\alpha_m\frac{m^2}{\sum_{j=1}^{m}2^{-M[j]}}.
$$

其中 `αₘ` 是修正系统偏差的常数。分母把每个寄存器的观测转换到规模的倒数，再以类似调和平均的方式汇总。与直接平均 `2^{M[j]}` 相比，它降低了少数异常大寄存器对结果的支配。

[HyperLogLog 原论文](https://algo.inria.fr/flajolet/Publications/FlFuGaMe07.pdf)给出的典型相对标准误差约为：

$$
\frac{1.04}{\sqrt{m}}.
$$

这不是“每次误差都不超过该值”的保证，而是估算分布的标准误差。例如 1024 个寄存器对应约 3.25%，16384 个寄存器对应约 0.81%。增加寄存器能按平方根规律提高精度，也会等比例增加摘要空间。

## 可执行示例复现更新、估算与合并

同目录的[完整 Node.js 示例](./hyperloglog.mjs)使用 SHA-256 的前 64 位作为哈希，建立 1024 个寄存器。两条数据流各有 30000 个不同值，其中 10000 个重叠；合并后的精确并集为 50000。

```sh
node hyperloglog.mjs
```

示例固定生成输入，因此输出可重复。它还会重复加入 1000 个已有值，检查所有寄存器是否保持不变。该实现用于解释算法，没有实现生产级 HLL++ 的稀疏编码和经验偏差表。

在 Node.js 24.21.0 上得到：

```text
registers=1024
expected-standard-error=3.25%
stream-a exact=30000 estimate=29836
stream-b exact=30000 estimate=28947
union exact=50000 estimate=48732
duplicates-changed=false
```

这一次确定性输入的三个估计都落在理论标准误差所描述的正常波动范围内，但单次结果不能用来反推实现永远具有同样误差。`duplicates-changed=false` 则直接验证了重复值不会改变寄存器。

合并两个摘要时，无须回放原始元素，只需逐寄存器取最大值：

```js
const merged = left.map((value, index) => Math.max(value, right[index]));
```

原因是对任意两个集合 A、B，都有：

$$
\max(\max_{x\in A}\rho(x),\max_{x\in B}\rho(x))
=\max_{x\in A\cup B}\rho(x).
$$

`max` 还满足交换律、结合律和幂等律。分片可以按任意顺序合并，重复收到同一摘要也不会改变结果，这让 HLL 很适合分布式聚合。不过，只有使用相同哈希规则、哈希宽度、精度 p 和寄存器解释的摘要才能直接合并。

## 小基数不能照搬原始估算式

输入还很少时，大量寄存器为 0，原始公式的偏差较明显。经典算法会在这一范围使用 linear counting：若 V 是仍为 0 的寄存器数量，则估算为：

$$
E_{small}=m\ln\frac{m}{V}.
$$

直觉上，空桶越少，投入的不同元素越多。示例在原始估算不超过 `2.5m` 且仍有空桶时采用这个修正。这里的阈值属于经典算法定义，不应被理解为所有实现都必须使用同一切换策略。

[Google 的 HyperLogLog++ 论文](https://research.google.com/pubs/archive/40671.pdf)进一步使用 64 位哈希、稀疏表示和经验偏差修正，改善小基数区间的空间与精度。具体数据库可能还有自己的编码、缓存和阈值，因此不能拿教学实现的字节布局去解析生产系统中的摘要。

## 它回答“多少”，不回答“是谁”

HLL 丢弃了元素本身，因而不能列出成员、检查某个值是否存在，也不能在事后恢复精确集合。它适合独立访客数、不同查询数、不同设备数等允许小幅统计误差的指标，不适合计费、权限判断或必须逐项审计的去重结果。

还有几项容易忽略的边界：

- 哈希必须足够均匀，哈希位数也限制可可靠表示的最大基数。面对攻击者可控输入时，还要考虑哈希碰撞和拒绝服务风险，不能把概率模型直接当成安全保证。
- 合并摘要能估算并集，但不能直接得到交集。用 `|A| + |B| - |A∪B|` 间接相减时，三个估计误差会累积；交集相对很小时尤其不稳定。
- `PFCOUNT` 等接口返回的是估计值，不应在业务代码中伪装成精确计数。[Redis 的官方文档](https://redis.io/docs/latest/commands/pfcount/)明确说明其 HLL 使用固定小空间并给出 0.81% 标准误差；多键调用计算的是摘要并集。
- 摘要只在参数兼容时可合并。系统升级哈希函数或精度前，需要设计版本标识和迁移策略，不能混合新旧寄存器后继续解释结果。

HyperLogLog 的核心不是“前导零等于元素数量”，而是把均匀哈希产生罕见模式的概率反推为样本规模。分桶提供多次独立观察，调和式汇总控制极端值，小基数修正补上空桶信息，而逐寄存器最大值则保留了并集语义。最终得到的是一份很小、可合并、误差可估计的基数摘要，而不是被压缩后的集合。
