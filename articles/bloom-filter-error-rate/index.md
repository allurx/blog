如果只想知道一个键是否存在，保存完整集合有时仍然太贵。Bloom Filter（布隆过滤器）把集合压缩成一段位数组，允许把少数不存在的键回答为“可能存在”，以换取较小的存储开销。它适合放在昂贵的精确查询之前：先排除确定不存在的键，再让剩余请求访问真实数据。

这个结构常被概括为“可能误判，不会漏判”。但这句话没有直接回答两个问题：误判概率如何由空间和插入量决定？配置的“1%”究竟是不是保证？本文讨论只插入、不删除的标准 Bloom Filter，从置位过程推导容量公式，再用 Python 3.12 标准库复现实验。理解过程只需知道哈希函数把键映射到数组位置，以及独立事件的概率如何相乘。

## 位数组记住了位置，却没有记住归属

设数组有 `m` 个二进制位，初始全为 0。插入一个键时，用 `k` 个哈希函数得到位置，把这些位置设为 1。查询同一个键时重新计算这些位置：只要有一个位置为 0，就回答“不存在”；全部为 1，只能回答“可能存在”。

下面用一个 8 位数组、每个键两个位置演示。位置仅为说明机制而指定，不是某种哈希函数的实测输出。

| 操作 | 访问的位置 | 结果 |
| --- | --- | --- |
| 插入 A | 1、4 | 位置 1、4 变为 1 |
| 插入 B | 4、6 | 位置 6 变为 1，位置 4 保持 1 |
| 查询未插入的 C | 1、6 | 两位均为 1，发生误判 |
| 查询未插入的 D | 0、4 | 位置 0 为 0，正确排除 |

C 的误判不需要它和 A 或 B 的所有哈希值完全相同。来自不同键的置位可以拼成 C 需要的组合。数组不保存“这一位由哪个键设置”，因此无法反向恢复证据的归属。

反过来，A 已经设置的位只要没有被清除，之后就一直为 1。这给出了无漏判的直接理由，甚至不需要假设哈希足够随机。随机性影响的是误判率；无漏判依赖的是插入完整、位单调置为 1，以及查询采用相同的键编码、哈希函数和参数并能看到已完成的写入。[Broder 与 Mitzenmacher 的综述](https://www.cs.cornell.edu/courses/cs619/2004fa/documents/BloomFilterSurvey.pdf)将这种单侧错误作为 Bloom Filter 的基本语义。

重复插入同一个键只会重复设置原来的位置。因此，下文的 `n` 是插入的**不同键的数量**，不是调用插入方法的次数。

## 先算一个位置为空的概率

为了估算误判率，先采用理想模型：不同键、不同哈希函数产生的位置相互独立，并且均匀分布在 `m` 个位置上。允许重复选中同一位置，也就是有放回选择。

一次哈希没有选中指定位置的概率是 `1 − 1/m`。插入 `n` 个不同键，共进行 `kn` 次选择，所以指定位置仍为 0 的概率为：

$$
q=\left(1-\frac{1}{m}\right)^{kn}.
$$

这在上述模型下是精确表达式。于是，数组中为 1 的位所占比例，其期望为 `1 − q`。当 `m` 足够大时，可以进一步近似：

$$
q\approx e^{-kn/m}.
$$

若暂时把实际置位比例当成这个平均值，未插入键的 `k` 次查询全部落在 1 上的概率就近似为：

$$
p_{\mathrm{FP}}\approx
\left[1-\left(1-\frac{1}{m}\right)^{kn}\right]^k
\approx\left(1-e^{-kn/m}\right)^k.
$$

这里的 `FP` 指 false positive，即不存在却被回答为可能存在。统计误判率时，分母是**未插入键的查询数**，不是全部查询数；如果业务请求多数本来就存在，总请求中的误判占比会是另一项指标。

## 为什么保留有限 m，也没有得到精确误判率

上式有两层近似。除了用指数函数近似幂，还把随机变化的置位比例替换成了平均值。第二步不能因为哈希函数独立就自动成立。

令 `X` 表示一次构建后实际为 1 的位数。给定这段位数组，一个独立的未插入键，其每次查询落在 1 上的概率为 `X/m`。在理想模型中，条件误判率就是 `(X/m)^k`。对所有可能的构建结果取平均，才得到整体误判率：

$$
p_{\mathrm{FP}}=\mathbb{E}\!\left[\left(\frac{X}{m}\right)^k\right].
$$

一般不能把“先乘方再平均”换成“先平均再乘方”。`k ≥ 2` 时，乘方还会放大置位比例偏大的那些构建结果。

一个可以完全枚举的例子是 `m = 2、k = 2、n = 1`：插入键的两个位置有一半概率相同，数组只有一位为 1，此时未插入键误判的概率是 `1/4`；另一半概率选中不同位置，两位都为 1，此时所有查询都会回答可能存在。因此：

$$
p_{\mathrm{FP}}=\frac12\cdot\frac14+\frac12\cdot1
=\frac58.
$$

而把平均置位比例直接平方，得到的却是 `(3/4)² = 9/16`。这个反例及对常见推导的纠正见 [Bose 等人的论文](https://cglab.ca/~morin/publications/ds/bloom-submitted.pdf)。它说明常用公式适合估算，不能无条件当作精确值，更不能直接当作误判率上限。

## 容量公式为什么对应大约一半的位被占用

现在回到常用的指数近似。固定空间 `m` 和插入量 `n`，增加 `k` 有两种相反作用：查询要满足更多位置，似乎更严格；但每次插入也设置更多位置，让整个数组更拥挤。因此哈希次数并非越多越好。

把 `k` 暂时当成连续变量，令 `a = n/m`，对近似误判率的对数求导：

$$
\frac{d}{dk}\log\left[(1-e^{-ak})^k\right]
=\log(1-e^{-ak})+\frac{ak e^{-ak}}{1-e^{-ak}}.
$$

在 `ak = ln 2` 时，右侧为 `−ln 2 + ln 2 = 0`。该近似模型的最优点为：

$$
k_{\mathrm{opt}}=\frac{m}{n}\ln2.
$$

此时空位比例约为 `e^(−ln 2) = 1/2`，置位比例也约为一半。将最优 `k` 代回，再用目标概率 `p` 解出容量，可得：

$$
\frac{m}{n}\approx-\frac{\ln p}{(\ln2)^2}.
$$

因此，每个不同键需要多少位，主要由目标误判率决定。例如目标为 1% 时约需每键 9.585 位。`n = 1000` 时将 `m` 向上取整得到 9586 位；再比较连续最优点两侧的合法整数 `k`，本例选择 7。[Boost.Bloom 的 FPR 估算说明](https://www.boost.org/doc/libs/latest/libs/bloom/doc/html/bloom.html#bloom_fpr_estimation)也明确采用相邻整数比较。

取整之后还应代回公式检查。本例的指数近似为 **1.0035%**，已经略高于最初输入的 1%。所以这个输入是容量规划目标，不是硬上限。如果业务对误判成本敏感，应预留空间，依据真实键分布与查询负载验证，并在插入量增长时重新评估。

9586 位用字节数组存储需要向上取整到 1199 字节。这只是位数组的有效载荷，不包含 Python 对象、解释器和实验中生成的字符串等内存。

## 用同一个过滤器观察插入量翻倍后的变化

完整程序见 [bloom_filter_demo.py](./bloom_filter_demo.py)。它只依赖 Python 标准库，使用字节数组真正按位存储；每次哈希都给键加上固定四字节序号前缀，再计算 SHA-256 并对 `m` 取模。这样可以得到稳定、可复现的多个位置，避免使用会受到进程随机化影响的内置字符串 `hash()`。

这个实现用于讲解。不同前缀不等于数学上已经证明哈希独立，取模也不构成严格均匀分布的证明；实验以 SHA-256 输出近似均匀为建模依据，不把它当成性能优化方案或生产级并发容器。

插入与查询的核心如下，完整的哈希实现、参数计算和入口都在附件中：

```python
def add(self, key: bytes) -> None:
    for position in self.positions(key):
        self.bits[position // 8] |= 1 << (position % 8)

def might_contain(self, key: bytes) -> bool:
    return all(
        self.bits[position // 8] & (1 << (position % 8))
        for position in self.positions(key)
    )
```

程序先枚举前文小例子的全部 16 种位置组合。然后固定 `m = 9586、k = 7`，依次插入 `member:0` 到 `member:999`，再追加到 `member:1999`。两个阶段都查询同一组 `absent:0` 到 `absent:99999`；这 100000 个键明确不属于插入集合，因此阳性回答都可计为误判。每个阶段还查询全部已插入键，统计漏判。

将附件保存到本地，在其所在目录运行：

```sh
python3 bloom_filter_demo.py
```

在 Linux、CPython 3.12.14 下得到以下输出。固定编码、输入和哈希算法让结果可以重复：

```text
tiny: exact=5/8, shortcut=9/16
m=9586, k=7, payload_bytes=1199
n=1000, set_bits=4921, false_negatives=0, false_positives=865/100000, observed=0.8650%, estimated=1.0035%
n=2000, set_bits=7314, false_negatives=0, false_positives=14970/100000, observed=14.9700%, estimated=15.7405%
```

`estimated` 是由 `m、k、n` 计算的指数近似，`observed` 是固定测试集上的误判比例。两者不必相等：真实哈希不是随机函数抽样的数学证明，实际位数组的置位数量也会偏离模型期望，有限查询集还会带来样本差异。这次较低的实测率不能证明所有输入都优于规划值。

更值得观察的是两个阶段的变化：空间和哈希次数不变，不同键的数量翻倍后，置位数从 4921 增至 7314，实测误判率升到约 15%。程序没有因为超过预计容量就拒绝插入，原有键也没有丢失；过滤器只是越来越难排除不存在的键。两个阶段漏判均为 0，这是本次运行的检查结果，而无漏判的一般依据仍是前面的单调置位推理。

## 把概率承诺放回实际系统

标准 Bloom Filter 无法安全地直接删除一个键。前面的 A、B 共用位置 4，如果删除 A 时把位置 4 清零，B 就可能被漏判。位数组没有记录共享关系，清位不能作为插入的逆操作；需要删除能力时，应另选支持该操作的数据结构及其正确实现。

并发同样需要单独处理。两个线程对同一字节执行非原子的“读取、按位或、写回”，可能覆盖彼此设置的不同位。这里丢失的是插入结果，而不是概率公式突然失效。例如 [Guava 33.4.8 的 API 文档](https://guava.dev/releases/33.4.8-jre/api/docs/com/google/common/hash/BloomFilter.html)说明其 BloomFilter 从 23.0 起借助原子操作和 CAS 保证并发访问的正确性。本文的 Python 示例只做顺序执行，没有提供这种保证。

如果把过滤器用于数据库前置判断，还必须回答“它表示哪个时刻的哪些数据”。一条记录已进入数据库，却尚未进入过滤器，此时过滤器回答不存在并不违反其内部集合的语义，但直接拒绝请求会成为业务层面的漏查。同步、重建和切换期间，能否用阴性结果排除真实数据，需要系统另外建立一致性条件。

在这些条件成立时，阴性结果才适合用来节省一次精确查询；阳性结果则应继续查真实数据。Bloom Filter 的空间收益来自丢弃键与位之间的归属信息，而误判率、容量边界和删除限制，都是这项取舍的具体后果。
