传统传输层实现通常用源 IP、源端口、目的 IP、目的端口组成的四元组区分通信流；把协议号也算进去，就是常说的五元组。这个办法默认一条连接使用同一条网络路径。手机从 Wi-Fi 切到蜂窝网络，或者 NAT 重新分配外部端口后，四元组随之改变，旧连接很难仅凭新报文继续匹配。

QUIC 仍通过 UDP 在具体路径上发送数据，却把“连接是谁”与“当前从哪条路径到达”拆开。报文头中的 Connection ID 标识连接状态，IP 地址与端口描述当前路径。两者分离后，端点可以在地址变化时保留加密上下文、流和应用会话，再对新路径单独验证可达性与拥塞状态。

本文讨论 [QUIC version 1](https://www.rfc-editor.org/rfc/rfc9000.html) 的单路径迁移。它不等同于任意服务器地址迁移或同时聚合多条路径，也不意味着 Connection ID 能替代密码学认证。

## 四元组同时承担身份和路径会发生什么

假设客户端最初通过家庭 Wi-Fi 连接服务器：

```text
client 192.0.2.10:53000  ──UDP──>  server 198.51.100.20:443
```

连接建立后，客户端离开 Wi-Fi，蜂窝网络为它提供另一个地址和端口：

```text
client 203.0.113.7:61000  ──UDP──>  server 198.51.100.20:443
```

服务器若只以四元组查表，第二行会像一条全新的 UDP 流。旧连接里的 TLS 密钥、QUIC Stream、流量控制额度和已经确认的数据都无法自然归到新报文上。客户端只能重新建立连接，再由应用恢复请求或会话。

地址改变也不一定是用户主动切网。NAT 可以在映射超时、设备重启或流量改走另一出口后分配新端口，这称为 NAT rebinding。对端看到的源地址发生变化，但客户端甚至可能不知道中间发生了重绑定。

四元组并没有失去价值。它仍准确描述一条发送路径，并参与路由、路径最大传输单元、往返时间和拥塞控制。问题只是不能再让它同时充当整条 QUIC 连接不可变的身份证明。

## Destination Connection ID 指向接收方的连接状态

[RFC 8999 的 QUIC 不变量](https://www.rfc-editor.org/rfc/rfc8999.html#section-5.3)把 Connection ID 定义为不透明字段，其首要作用是在 UDP、IP 或更低层地址变化后，仍把报文交给正确的 QUIC 端点实例。

QUIC 报文中最重要的是 **Destination Connection ID（DCID）**。接收方先前选择这个值并交给发送方，发送方把它放在后续报文头里。报文到达时，接收方用 DCID 找回连接状态：

```text
发送方向                          报文头中的 DCID              接收方用途
client  ──────────────────────>  server-issued CID  ───────>  定位服务器连接状态
server  ──────────────────────>  client-issued CID  ───────>  定位客户端连接状态
```

长报文头还可以携带 Source Connection ID（SCID），告诉对方回包时应使用哪个 DCID。握手完成后的短报文头只携带 DCID，其长度由此前的协商上下文确定，不在每个短报文中重复编码。

“每一端为自己接收的报文发放 ID”是理解方向的关键。服务器发给客户端的 Connection ID，不是客户端身份，而是客户端以后用来寻址服务器连接状态的值。这样服务器可以选择适合自身路由与状态管理的格式，客户端也对反方向做同样的事。

一条连接并不只有一个永久 CID。[RFC 9000 的 Connection ID 管理](https://www.rfc-editor.org/rfc/rfc9000.html#section-5.1)允许每端为对方准备一组可替换值。Connection ID 因而更像由接收方签发、可轮换的连接句柄，而不是连接建立时写死的公开序号。

## 地址变化后先匹配连接，再验证新路径

客户端换网后，可以从新的源地址发送受当前连接密钥保护的报文，并使用服务器此前签发的 DCID。服务器按 DCID 找到旧连接，成功移除报文保护后，知道报文属于持有连接密钥的一方；但这还不能证明报文头里的新源地址确实可接收返回流量。

攻击者可能伪造受害者地址，诱使服务器把大量数据发送给受害者。即使攻击者无法伪造受保护的 QUIC 载荷，实现也不能因为看见一个新地址就无条件把全部流量切过去。因此，连接识别与路径可达性验证是两个阶段：

1. 用 DCID 与报文保护把数据归入已有连接。
2. 用 `PATH_CHALLENGE` 和 `PATH_RESPONSE` 验证新的地址与端口组合。

[RFC 9000 的 Path Validation](https://www.rfc-editor.org/rfc/rfc9000.html#section-8.2)规定，端点向新路径发送包含不可预测 8 字节数据的 `PATH_CHALLENGE`；对端在同一路径返回携带相同数据的 `PATH_RESPONSE`。挑战值提供足够熵，普通 ACK 不能代替这项检查。

```text
client(new address)                             server
        │  受保护报文，携带已有 DCID               │
        ├────────────────────────────────────────>│  匹配旧连接
        │                                         │
        │             PATH_CHALLENGE(token)       │
        │<────────────────────────────────────────┤
        │             PATH_RESPONSE(token)        │
        ├────────────────────────────────────────>│  新路径验证完成
```

路径验证证明的是“对端能在这个地址收到挑战并返回正确响应”，不是重新认证对端身份。连接身份依赖握手建立的密钥和报文完整性保护；Path Validation 负责降低源地址伪造和流量放大的风险。新路径验证完成前，端点还要遵守未验证地址的发送限制，不能把迁移变成反射放大器。

验证也有方向。一个端点验证自己向对方发送的路径是否可达，不自动证明反方向已经验证；双方按各自需要完成检查。规范同时明确，这套机制不是完整的 NAT 穿透协议，它没有提供两个受限端点协调用于打洞的信令。

## 连接状态可以延续，路径状态不能照搬

迁移成功不代表所有旧状态都适合新网络。QUIC 把状态按作用范围分开处理。

连接级状态可以继续使用，包括：

- 握手产生的加密上下文与对端身份；
- 已建立的 QUIC Stream 及其读写进度；
- 连接级和流级的流量控制状态；
- 已发送、已确认和仍需重传的数据关系；
- 应用层在该连接上的会话，例如 HTTP/3 请求。

路径级状态则需要重新评估。新的 Wi-Fi、蜂窝网络或 NAT 出口可能具有完全不同的带宽、往返时间、最大数据报大小和 ECN 支持。若直接沿用旧路径较大的拥塞窗口，端点可能瞬间压垮更慢的新链路。

[RFC 9000 的迁移章节](https://www.rfc-editor.org/rfc/rfc9000.html#section-9.4)要求发送方在确认迁移后重置拥塞控制和 RTT 估计，并在新路径重新验证 ECN。路径最大传输单元也不能因为旧路径成功发送过大数据报就直接继承。Connection ID 保住的是连接连续性，不是对新网络能力的承诺。

这项边界解释了 QUIC 迁移为何不是“改一下 IP 继续发”这么简单：逻辑会话延续与网络条件重置必须同时发生。保留太少会失去迁移价值，保留太多又会把旧路径的错误假设带到新路径。

## 为什么迁移时还要更换 Connection ID

如果客户端在家庭 Wi-Fi 和蜂窝网络上始终携带同一个可见 CID，两个网络中的被动观察者就能用它关联用户迁移前后的流量。Connection ID 解决了四元组变化后的连续性，却也可能变成更稳定的跟踪标识。

因此，[RFC 9000 的迁移隐私要求](https://www.rfc-editor.org/rfc/rfc9000.html#section-9.5)规定，端点从不同本地地址发送时不能重复使用同一个 Connection ID，也不能对不同目的地址复用同一个 CID。迁移到新路径时，应从对方预先提供的连接 ID 池中选择一个尚未在其他路径使用的值。

可轮换 ID 通过两个加密帧管理：

| 帧                         | 发送方表达的含义                                               |
| -------------------------- | -------------------------------------------------------------- |
| `NEW_CONNECTION_ID`        | 提供一个带序号的新 CID，以及与它关联的 Stateless Reset Token   |
| `RETIRE_CONNECTION_ID`     | 表示不再使用某个序号的 CID，并请求对方补充可供以后使用的值     |

`NEW_CONNECTION_ID` 还带有 `Retire Prior To`，让签发方要求对端停用某个序号以前的旧 ID。每端维护对方提供的可用集合，也要继续识别尚未完成退役的旧值，以容忍报文丢失和重排。[帧格式与约束](https://www.rfc-editor.org/rfc/rfc9000.html#section-19.15)确保同一序号不能被悄悄绑定到不同 CID 或不同重置令牌。

轮换只能降低直接关联，不能保证完全匿名。报文时间、长度、迁移前后的网络位置和应用行为仍可能暴露关联。实现还要生成外部观察者难以相互关联的 CID；仅仅把计数器从 7 改成 8，并没有获得实际隐私。

## 负载均衡器也必须识别同一连接

服务器集群的入口常先经过四层负载均衡器。若它只对四元组哈希，客户端换网后就可能被转发到另一台后端，而新后端没有旧连接的密钥和 Stream 状态。端点本身支持迁移，并不能自动让前面的路由基础设施获得同样能力。

一种做法是让服务器签发的 CID 携带经过保护的路由信息，负载均衡器据此把新四元组的报文仍送到持有连接状态的后端。[QUIC 适用性说明](https://www.rfc-editor.org/rfc/rfc9308.html#section-11.1)专门指出，服务器生成的 Connection ID 可以编码服务器或负载均衡池标识，以支持无状态负载均衡。

这不是要求所有 CID 都明文暴露服务器编号。编码方案需要在可路由性、密钥轮换、长度、不可关联性和运维复杂度之间取舍。负载均衡器不理解 CID 时，也可以依赖共享连接状态或其他一致路由机制；无论采用哪种方案，基础设施都要保证迁移后的报文到达正确实例。

## 零长度 CID 主动放弃了迁移能力

QUIC 允许端点选择零长度 Connection ID。这样报文不再携带用于定位该接收方连接状态的 DCID，端点只能借助本地地址、端口以及其他网络信息区分连接。好处是减少报文头开销，也避免暴露一个额外标识。

代价是地址变化后无法再可靠匹配原连接。[RFC 9308](https://www.rfc-editor.org/rfc/rfc9308.html#section-11)明确说明，选择零长度 CID 的端点可能无法在 NAT rebinding 或迁移后把数据报关联回连接。它也不能再向对方签发新的 CID，`NEW_CONNECTION_ID` 和 `RETIRE_CONNECTION_ID` 在这种方向上都不适用。

这项选择适合明确不需要迁移、连接数量可由固定地址端口区分的受控场景。面向移动网络、长连接或多实例服务时，节省几个字节通常不值得失去路径变化后的连续性与路由能力。

## Connection ID 不是认证令牌

CID 通常在可见的 QUIC 头部中传输，网络观察者可以读取并复制。它的职责是把报文送到候选连接状态，而不是证明发送者合法。接收方仍必须完成报文解密和完整性校验，无法通过保护的报文不能因为 CID 命中就进入连接状态机。

同样，知道一个 CID 也不能任意接管连接或触发无限发送。路径验证、未验证地址上的放大限制、拥塞控制和包保护共同约束迁移。Connection ID 只是把“先找到哪份状态”这个问题从地址中抽离，安全性来自它与其他协议机制的组合。

当端点已经丢失连接状态时，CID 还可以与 Stateless Reset Token 关联，使端点无需保留完整连接也能生成难以伪造的无状态重置；对端识别令牌后立即放弃失效连接。[Stateless Reset](https://www.rfc-editor.org/rfc/rfc9000.html#section-10.3)是故障清理机制，不会恢复连接，也不把 CID 变成秘密。

QUIC 的设计重点不是抛弃四元组，而是缩小它的职责：四元组描述路径，Connection ID 定位连接，报文保护认证连接参与者，Path Validation 检查新路径的可达性。迁移时，连接级状态得以延续，拥塞与 RTT 等路径级状态重新建立，CID 也随路径轮换以减少关联。正是这种职责分离，让一次地址变化不必等价于一次应用会话重启。
