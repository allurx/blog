TCP 接收方拿到一段乱序数据时，普通确认号只能停在缺口之前。选择性确认（Selective Acknowledgment，SACK）可以另外告诉发送方：缺口之后的哪些字节已经收到。既然 SACK 更精确，为什么 TCP 没有用它替换原来的累计 ACK？

原因在于两者表达的承诺不同。累计 ACK 给出一条连续、单调推进的交付边界；SACK 描述边界之外当前缓存的离散区间。发送方利用后者减少无谓重传，但仍以累计 ACK 判断哪些数据已经得到最终确认。本文按字节序号跟踪一次丢包恢复，说明这两类信息如何配合。讨论以 TCP 基本规范 [RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)、SACK 选项规范 [RFC 2018](https://www.rfc-editor.org/rfc/rfc2018.html)和基于 SACK 的保守恢复算法 [RFC 6675](https://www.rfc-editor.org/rfc/rfc6675.html)为依据。

## 累计 ACK 只推进连续前缀

TCP 为字节流中的每个字节分配序号。报文段头部的 `Acknowledgment Number` 表示接收方下一步期望的序号；确认号为 $X$，意味着所有小于 $X$ 的字节都已收到。RFC 9293 将这种语义定义为[累计确认](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.4)：只要连续前缀中仍有缺口，确认号就不能越过它。

假设发送方依次发出四段数据，区间统一写成左闭右开形式：

| 报文段 | 字节区间        | 接收结果 |
| ------ | --------------- | -------- |
| A      | `[1000, 2000)`  | 丢失     |
| B      | `[2000, 3000)`  | 已收到   |
| C      | `[3000, 4000)`  | 已收到   |
| D      | `[4000, 5000)`  | 已收到   |

接收方缺少序号 1000 开始的数据，所以普通确认号仍是 `ACK=1000`。它不能发出 `ACK=5000`：发送方会按累计语义把 5000 之前的所有字节视为已经确认，进而错误地释放 A 的副本。

这条边界很容易维护。发送方用 `SND.UNA` 记录最早尚未确认的序号，收到更大的有效累计 ACK 后向前移动它；不超过新确认号的报文段才可以从重传队列中删除。接收方补上缺口后，也能一次把边界跨过已经缓存的连续数据。若重传的 A 随后到达，上例的确认号会直接从 1000 前进到 5000。

## SACK 把缺口后的缓存状态带回来

累计确认无法区分两种情况：接收方只拿到了 B，还是已经拿到 B、C、D。SACK 选项补充的正是这部分信息。支持 SACK 的双方先在建立连接的 `SYN` 中使用 `SACK-Permitted` 选项协商；之后接收方可以在 ACK 中携带一个或多个 SACK 块。每个块的左边界是已收到连续区间的第一个序号，右边界是该区间之后的第一个序号。

在上例中，D 到达后，接收方可以回复：

```text
ACK = 1000
SACK = [2000, 5000)
```

两个字段没有矛盾。`ACK=1000` 表示“1000 是连续字节流的下一个缺口”，SACK 块表示“2000 到 4999 当前已在接收缓存中”。RFC 2018 要求第一个 SACK 块报告[触发该 ACK 的最新数据](https://www.rfc-editor.org/rfc/rfc2018.html#section-4)，后续块可以重复此前报告过的区间，让有限的 TCP 选项空间优先携带最有用的信息。

发送方把这些区间记入常称为 *scoreboard* 的状态中。它由累计 ACK 和历次 SACK 信息共同更新，可以回答两个不同问题：

- `SND.UNA` 之前的数据已经得到累计确认，可以安全释放；
- `SND.UNA` 之后哪些数据被选择性确认，哪些区间仍像是网络中的“洞”。

因此，SACK 的直接收益不是改变可靠交付语义，而是缩小重传范围。在一个窗口内丢失多段数据时，发送方不必重传接收方明确报告仍持有的区间。

## SACK 块不是不可撤回的交付凭证

发送方不能只凭 SACK 块就永久删除数据。RFC 2018 明确允许接收方在内存压力下丢弃已经选择性确认、但尚未纳入累计确认的数据，这种行为称为 *reneging*。规范不鼓励这样做，却要求发送方能够正确应对。

这个边界解释了两种确认必须共存的根本原因：

1. 累计 ACK 表示连续前缀已经被接收，发送方可以据此清理重传队列；
2. SACK 表示接收方当前报告持有的离散区间，用于安排恢复，但这份报告可能在累计边界推进前失效。

[RFC 2018 的 reneging 规则](https://www.rfc-editor.org/rfc/rfc2018.html#section-8)要求接收方不要继续报告已经丢弃的旧区间；发送方仍须保留相应数据，直到累计 ACK 覆盖它们。发生重传超时也要格外谨慎：[RFC 6675 第 5.1 节](https://www.rfc-editor.org/rfc/rfc6675.html#section-5.1)说明，超时可能意味着接收方撤回了先前的 SACK 信息，恢复决策不能盲目信任旧状态。

## SACK 帮助判断损失，但不单独决定重传

一个 SACK 块只能证明某些较高序号的数据已经到达，不能单独证明较低序号的数据永久丢失。网络重排也会让后发数据先到。发送方需要把 SACK 证据与重复 ACK、拥塞窗口和恢复状态结合起来，达到一定阈值后才把某个区间判为丢失。

RFC 6675 描述了一套保守算法：`HighACK` 表示累计确认的最高序号，scoreboard 记录选择性确认的区间，`IsLost()` 根据缺口之后已经选择性确认的报文段数量或字节数判断缺口是否可视为丢失。进入恢复后，发送方优先重传这些洞，同时用 `Pipe` 估计仍在网络中的数据量，避免恢复过程绕过拥塞控制。

这里有三个容易混淆的层次：

| 信息或状态       | 回答的问题                                 | 主要作用               |
| ---------------- | ------------------------------------------ | ---------------------- |
| 累计 ACK         | 哪个连续前缀已经确认？                     | 推进可靠交付边界       |
| SACK 块          | 边界之外哪些离散区间当前已收到？           | 建立 scoreboard        |
| 丢失恢复算法     | 哪些未确认区间已有足够证据需要重传？       | 调度重传并约束在途数据 |

把这三层分开，就不会把“已选择性确认”误解成“已经最终确认”，也不会把一个乱序到达的报文段直接当作丢包证据。

## 缺口补齐后由累计边界收束状态

回到最初的例子。发送方根据重复确认和 SACK 信息重传 `[1000, 2000)`；接收方拿到它后，缓存中的 `[1000, 5000)` 形成连续区间，于是回复 `ACK=5000`。这个累计 ACK 覆盖 A、B、C、D，发送方可以统一释放相应重传数据，旧 SACK 块也失去作用。

SACK 让恢复过程看见累计边界之外的细节，累计 ACK 则把这些暂时、离散的信息最终收束成一条稳定边界。前者提高多重丢包时的重传效率，后者维持 TCP 字节流可靠确认的简单契约。它们解决的是不同层次的问题，所以更精确的 SACK 选择了补充累计 ACK，而不是替代它。
