TLS 1.3 的 0-RTT 可以让客户端在恢复连接时，不等服务器回传 `ServerHello` 就发送应用数据。请求仍经过加密和完整性保护，旁路攻击者看不到明文，也不能随意修改内容。然而，攻击者可能原样复制这批密文，让服务器在另一条连接上再次处理同一个请求。

加密解决的是保密性和篡改检测，重放保护还需要确认“这份合法密文以前是否处理过”。普通 TLS 1.3 应用数据绑定了本次握手中新生成的服务器随机量，0-RTT 数据却必须在收到服务器新消息之前产生。本文从早期密钥的来源解释这个缺口，再说明服务器防重放机制、HTTP `425 Too Early` 和应用幂等性各自能保护到哪里。

## 0-RTT 用旧会话建立早期密钥

客户端完成一次 TLS 1.3 握手后，服务器可以发送 `NewSessionTicket`。票据让双方在后续连接中使用预共享密钥（PSK）恢复会话，免去完整证书认证路径。服务器若在票据中同时允许 early data，客户端下次就可以在第一批报文中发送：

```text
ClientHello + early_data
```

客户端此时还没有收到新连接的 `ServerHello`，只能根据 PSK 和当前 `ClientHello` 的握手转录派生 early traffic secret，再用它保护 0-RTT 数据。[RFC 8446 第 2.3 节](https://www.rfc-editor.org/rfc/rfc8446.html#section-2.3)明确列出两项较弱的安全属性：早期数据不具备前向保密性，而且 TLS 不保证它在不同连接之间不会被重放。

0-RTT 省掉的正是等待服务器新鲜输入的一次往返。代价是服务器在处理早期数据时，还不能用本次握手的唯一结果证明“这批数据只属于这一条已完成的连接”。

## 攻击者不必解密，只需复制

假设客户端把一条 0-RTT 请求发给服务器实例 A。网络攻击者记录完整的 `ClientHello` 和早期数据，然后把相同字节转发给实例 B：

```text
客户端 ── ClientHello + 0-RTT 请求 ──> 实例 A
攻击者 ── 同一批已记录的字节 ────────> 实例 B
```

这两份数据都具有合法的认证标签。攻击者不知道 PSK，也没有修改密文；密码学验证因此不会自动拒绝第二份。若两个实例都接受同一会话票据，而且没有共享“已经见过这次 ClientHello”的状态，应用动作就可能执行两次。

TLS 仍能阻止一些更强的攻击。相同数据不能在同一条连接中冒充两个不同的记录，0-RTT 密文也不能伪装成握手后的 1-RTT 数据，因为两者使用不同密钥。缺少的是[RFC 8446 第 8 节](https://www.rfc-editor.org/rfc/rfc8446.html#section-8)所说的跨连接固有防重放保证。

这与客户端正常重试也不同。重试由客户端在超时或明确响应后发起；重放可以由攻击者完成，客户端并不知道请求出现了第二份。两者最终都会造成重复效果，所以应用层通常需要同一套去重或幂等设计，但威胁来源不能混为一谈。

## 服务器防重放需要共享状态或缩小窗口

TLS 服务器可以降低重放成功率，常见方法有两类：

1. **一次性会话票据**：某张票据成功用于 0-RTT 后就不再接受它。服务器需要可靠记录票据使用状态。
2. **记录近期 ClientHello**：在票据有效窗口内保存能够识别早期数据尝试的信息，再拒绝重复值。

这些方法在单实例上容易实现，分布式部署却要决定状态共享范围。若每个边缘节点只维护本地记录，同一份早期数据仍可能分别被不同节点接受；若所有节点同步一个强一致的全局集合，延迟、可用性和存储成本又会抵消 0-RTT 的部分收益。服务器还要处理时钟偏差、票据生命周期和状态丢失，不能只检查客户端声称的票据年龄。

RFC 8446 的最低要求是：同一个服务器实例对同一次 0-RTT 握手至多接受一次，并在可行时进一步限制跨实例重放。规范也要求客户端只发送自己认为可以安全重复的数据，因为客户端通常不知道服务端究竟部署了多强的防重放状态。

这些机制只能限制次数和时间窗口，不能给应用提供绝对的“恰好一次”语义。[RFC 9325 对 0-RTT 的安全建议](https://www.rfc-editor.org/rfc/rfc9325.html#section-3.10)因此要求协议和应用明确规定何时可以使用早期数据，不能把 TLS 库打开 0-RTT 视为透明的性能开关。

## HTTP 用请求语义决定是否值得冒险

HTTP 对早期数据的处理由 [RFC 8470](https://www.rfc-editor.org/rfc/rfc8470.html)约束。客户端缺少额外信息时，可以用 0-RTT 发送安全方法，但不能发送不安全或安全性未知的方法。这里的“安全”指请求语义本质上只读，例如正常的 `GET` 和 `HEAD`；它比“重复执行后最终状态相同”的幂等性要求更严格。

这个区别很重要。`PUT` 和 `DELETE` 在 HTTP 语义上通常是幂等方法，却不是安全方法：即使多次执行后的资源状态相同，重复请求仍可能多记一次审计事件、重复触发通知，或者放大后端负载。反过来，一个名义上的 `GET` 若被错误设计为执行扣款，也不会因为方法名称安全就真的适合 0-RTT。

因此，服务器需要按资源和实际副作用判断风险，而不是只看方法名。典型分类如下：

| 请求                         | 默认是否适合 0-RTT | 主要风险                           |
| ---------------------------- | ------------------ | ---------------------------------- |
| `GET /static/app.css`        | 通常适合           | 重复读取和缓存压力                 |
| `GET /report?date=...`       | 视资源实现而定     | 昂贵计算、计费或访问计数被放大     |
| `POST /payments`             | 不适合             | 重复扣款或重复创建订单             |
| 带唯一幂等键的创建请求       | 仍需显式评估       | 去重范围、过期时间或跨区域状态不全 |

幂等键可以让应用把多次到达映射到同一个业务动作，但只有在所有可能接收请求的实例共享去重结果、键与请求内容绑定且保留时间覆盖重放窗口时才成立。它是业务层防线，不会改变 TLS 0-RTT 本身可被复制的事实。

## 425 让请求回到握手之后

网关往往知道请求来自早期数据，却不知道源站的业务操作能否安全重复。RFC 8470 定义了两个协调信号：

- 中间节点转发可能受重放影响的请求时，使用 `Early-Data: 1` 告知下游；
- 服务器不愿承担重放风险时，返回 `425 Too Early`。

客户端收到 425 后可以自动重试，但重试必须等 TLS 握手完成，不能再次放进 early data。这样，请求会使用本次连接的 1-RTT 密钥和完整握手上下文。425 表达的是“现在处理可能太早”，不是业务失败，也不应被默认缓存。

服务器还可以在 TLS 层整体拒绝 early data，或者先缓存请求，等握手完成后再交给应用。TLS 层拒绝无法逐个挑选早期请求；HTTP 层延迟处理和 425 则能结合资源语义做更细的决定。多层代理存在时，`Early-Data` 头不能随意删除，否则源站会失去判断这条请求是否可能已经在上一跳被处理过的依据。

## 降低一轮延迟不等于获得免费重试

0-RTT 把应用数据提前到客户端的第一批报文，换来的延迟收益来自“不等待服务器的新鲜输入”。同一设计也决定了早期数据不能天然绑定到唯一完成的连接。密文可以保持机密和完整，同时仍被原样复制并再次验证成功。

可靠使用 0-RTT 需要三层共同约束：TLS 层限制票据和重放窗口，HTTP 层用 `Early-Data` 与 425 协调处理时机，应用层只让可安全重复或具备可靠去重机制的操作进入早期数据。任何一层都不能单独承诺恰好一次。对于扣款、创建订单、发消息等有不可逆副作用的请求，等待握手完成通常比用一次往返换取复杂而不完整的防重放保证更合适。
