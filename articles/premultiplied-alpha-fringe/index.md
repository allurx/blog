一张红色图形放在透明背景上，原图边缘看起来正常，缩放、旋转或生成 mipmap 后却可能出现暗边。若透明像素的 RGB 不是黑色，边缘还会染上其他颜色。问题通常不在透明度精度，而在插值时把“像素携带的颜色”和“像素实际贡献的颜色”混在了一起。

预乘 Alpha（premultiplied alpha）先把 RGB 乘以 alpha，再对结果进行插值和合成。这样，完全透明像素的颜色贡献必然为零，半透明像素的数值也已经包含覆盖比例。本文用一个数值例子解释它为什么能消除色边，并说明 PNG、WebGL 与图像处理管线应当在哪一步转换表示。

## 直通 Alpha 会保留不可见的 RGB

常见 RGBA 像素有两种表示。**直通 Alpha**（straight alpha，也称 unassociated alpha）分别保存颜色 $C=(R,G,B)$ 和不透明度 $\alpha$：

$$
(C,\alpha).
$$

**预乘 Alpha**（premultiplied alpha，也称 associated alpha）保存颜色贡献 $c$：

$$
c=C\alpha,
$$

$$
(c,\alpha)=(R\alpha,G\alpha,B\alpha,\alpha).
$$

当 $\alpha=0$ 时，直通表示仍允许 RGB 是任意值。`rgba(0, 0, 0, 0)`、`rgba(255, 0, 0, 0)` 和 `rgba(0, 0, 255, 0)` 显示时都完全透明，却保留了不同的隐藏颜色。[PNG 第三版规范](https://www.w3.org/TR/png-3/#11alpha)明确使用这种非预乘表示，因此解码 PNG 后不能仅凭文件带 alpha 通道，就假设 RGB 已经乘过 alpha。

预乘表示没有这项歧义：归一化 RGB 必须满足 $0\le c\le\alpha$，所以完全透明像素只能是 `(0, 0, 0, 0)`。这不是把透明区域涂黑；它表示该像素对最终图像没有颜色贡献。

## 逐通道插值会让隐藏颜色进入边缘

考虑两个相邻像素：左侧是不透明红色，右侧是透明黑色。用直通 RGBA 表示为：

```text
A = (1, 0, 0, 1)
B = (0, 0, 0, 0)
```

双线性采样、缩放和纹理过滤都可能在两者之间取中点。若直接逐通道平均，得到：

$$
\operatorname{lerp}(A,B,0.5)=(0.5,0,0,0.5).
$$

这个中点只有 50% 不透明，但它的直通颜色也被透明像素拉成了 50% 红。把它合成到白色背景上，红通道的输出为 $0.5\times0.5+1\times(1-0.5)=0.75$，最终颜色是 `(0.75, 0.5, 0.5)`。边缘比应有结果更暗。

先预乘再插值时，两个端点仍分别为 `(1, 0, 0, 1)` 和 `(0, 0, 0, 0)`，但 RGB 的含义已经变成颜色贡献。中点为：

$$
(c,\alpha)=(0.5,0,0,0.5).
$$

解除预乘后，直通颜色是 $C=c/\alpha=(1,0,0)$。它表示“50% 覆盖的完整红色”，合成到白色后得到 `(1, 0.5, 0.5)`。红色强度没有被透明区域中的黑色稀释。

两个中点的四个存储数值看起来相同，语义却不同：前者把 `0.5` 当作尚未乘 alpha 的红色，合成时还要再乘一次；后者的 `0.5` 已经是红色贡献，不能重复乘 alpha。若透明端点藏着蓝色，直通插值还会让边缘偏紫；预乘后该端点的蓝色贡献仍为零。

## 预乘空间直接插值颜色贡献

把多个直通像素按权重 $w_i$ 过滤时，正确的覆盖率是：

$$
\alpha=\sum_i w_i\alpha_i.
$$

输出颜色应按每个样本的实际贡献加权：

$$
c=\sum_i w_i C_i\alpha_i.
$$

这两个式子正好是对预乘 RGBA 的四个通道做同一次线性过滤。需要直通颜色时，最后再计算 $C=c/\alpha$。若 $\alpha=0$，颜色没有可观察意义，应保留零值，不能除以零。

直接过滤直通 RGB 计算的是 $\sum_i w_i C_i$。它给每个像素的隐藏颜色相同权重，完全没有考虑该像素是否覆盖输出位置。只有当所有样本的 alpha 相同，或者透明像素的隐藏 RGB 恰好与邻近可见颜色一致时，两种计算才会碰巧相同。

[CSS Color 4 的带 Alpha 插值规则](https://www.w3.org/TR/css-color-4/#interpolation-alpha)也采用同一顺序：先把颜色分量乘以 alpha，再插值，最后在非零 alpha 下解除预乘。这项规则不只适用于两个颜色之间的渐变，也解释了图像重采样、模糊和 mipmap 生成为什么应在预乘表示下处理透明边缘。

## Source-over 合成在预乘表示中保持闭合

最常见的 source-over 合成把前景放在背景之上。设前景为 $(C_s,\alpha_s)$，背景为 $(C_b,\alpha_b)$，输出 alpha 为：

$$
\alpha_o=\alpha_s+\alpha_b(1-\alpha_s).
$$

使用直通颜色时，必须先计算预乘贡献，再除以输出 alpha：

$$
C_o=\frac{C_s\alpha_s+C_b\alpha_b(1-\alpha_s)}{\alpha_o}.
$$

使用 $c_s=C_s\alpha_s$ 和 $c_b=C_b\alpha_b$ 后，公式直接变为：

$$
c_o=c_s+c_b(1-\alpha_s).
$$

结果 $(c_o,\alpha_o)$ 仍是预乘表示，可以继续作为下一层合成的输入，不必在每一层除以 alpha。[W3C Compositing and Blending Level 1](https://www.w3.org/TR/compositing-1/#simplealphacompositing)正是用这个形式定义简单 alpha 合成。

预乘表示因此同时适合过滤和反复合成：线性运算处理的都是已经按覆盖率缩放的颜色贡献。它避免色边的原因不是计算次数更少，而是中间值始终保留了正确的物理含义。

## 文件格式、采样和混合状态必须一致

预乘不是一个可以只改变量名的约定。整条管线必须知道当前缓冲区使用哪种表示：

1. **解码**：PNG 的 RGB 是直通颜色。若后续要缩放、模糊、生成 mipmap 或合成，应先转换到计算所需的颜色空间，再乘 alpha。
2. **过滤**：在线性过滤、卷积和多级缩小期间保持预乘。若先用直通数据生成 mipmap，隐藏颜色造成的色边已经写入低分辨率层，之后再预乘无法恢复丢失的边缘颜色。
3. **混合**：直通源通常需要用源 alpha 缩放源 RGB；预乘源的 RGB 已经缩放，source-over 对源颜色使用因子 `ONE`，对目标颜色使用 `ONE_MINUS_SRC_ALPHA`。混用状态会造成重复乘 alpha 或完全不乘。
4. **输出**：需要写回 PNG 这类直通格式时，在 $\alpha>0$ 的像素上解除预乘；$\alpha=0$ 时写入约定的 RGB 值。反复预乘、量化再解除预乘会放大低 alpha 区域的舍入误差，应尽量在高精度中间缓冲区中完成处理。

WebGL 的上下文属性 `premultipliedAlpha` 描述页面合成器如何解释绘图缓冲区，不会自动替应用选择正确的纹理格式、着色器输出或 `blendFunc`。当它为 `true` 时，规范要求交给页面合成器的颜色满足预乘约束；具体绘制阶段仍需让数据表示和混合因子一致。[WebGL 1.0 规范的上下文创建属性](https://registry.khronos.org/webgl/specs/latest/1.0/#5.2)给出了这项契约。

## 预乘 Alpha 不替代线性光处理

Alpha 表示覆盖比例，本身不使用 sRGB 传递函数。预乘解决的是颜色与覆盖率如何一起插值和合成；[sRGB 不能直接按通道平均](/srgb-linear-color-mixing/)解决的是编码值与光强不成正比。两者是独立问题。

要求光能正确的完整顺序通常是：把 RGB 从 sRGB 解码到线性光，在线性 RGB 中乘 alpha，完成过滤或合成，必要时解除预乘，最后编码回输出颜色空间。直接在 sRGB 编码值中预乘可以消除一部分透明边缘污染，却不能修正非线性颜色混合产生的明暗误差。

直通表示仍有合理用途。图像编辑器可能需要保留完全透明区域的原始 RGB，某些颜色变换也需要先取得不受覆盖率影响的颜色。关键是把存储语义与计算语义分开：保留直通数据用于编辑，在进入插值和 source-over 合成之前转换为预乘形式，离开计算管线时再按目标格式转换。

透明边缘的色边并非 alpha 通道“漏色”，而是隐藏 RGB 在错误的表示中参加了过滤。预乘 Alpha 把每个像素改写成实际颜色贡献，使透明样本自然贡献零，使半透明样本按覆盖率参与运算。只要文件解码、滤波、混合和输出对表示保持一致，缩放、旋转和多层合成就不会再把不可见颜色带回可见边缘。
