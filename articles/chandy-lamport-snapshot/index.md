A 和 B 一共持有 100 枚代币。两边各存一份余额，再把这两份记录相加，结果却只有 93。少的 7 枚未必是账错了：B 已经扣了款，A 的那份记录却拍在收款之前。真正要问的是，能不能从这份快照继续运行，让这 7 枚恰好到账一次？

先把模型说清楚。A 和 B 各自按顺序处理事件，两个方向各有一条可靠的先进先出（FIFO）通道。同一条通道上的消息按发送顺序到达，两个方向之间没有先后保证。发送时扣减余额并把转账消息放入通道，接收时取出消息并增加余额，各算一个本地事件。这里没有数据库、外部支付系统，也没有丢包或重试。这个小模型足以看清 [Chandy 和 Lamport 的分布式快照算法](https://www.cs.princeton.edu/courses/archive/fall17/cos418/papers/chandy_lamport.pdf)解决了哪一层问题。

## 余额之间缺的，是通道的状态

在每个进程的事件序列上画一道线，只保留线以前发生的事。把各进程保留的片段合起来，称为一个**切面**。判断切面是否一致，有个直接的办法：如果保留了一次接收，它对应的发送也必须保留。再加上每个进程保留的都是从头开始的一段，这就不会留下一个没有原因的结果。

用这个办法看一笔转账，它在快照里的归属很明确：

| 扣款发送已保留 | 收款接收已保留 | 快照应该如何解释 |
| --- | --- | --- |
| 否 | 否 | 转账尚未发生，代币仍在发送方余额里 |
| 是 | 否 | 发送方已经扣款，转账消息属于通道 |
| 是 | 是 | 转账已经完成，代币在接收方余额里 |
| 否 | 是 | 不一致：接收方已经入账，发送方却没有扣款 |

第二行完全合法。接收端即使在制作快照期间把钱收了，只要它保存的余额不含这笔钱，快照就仍要把消息放在通道里。这里的“在途”是相对于两份**已保存的状态**而言，不是问制作快照结束时网络里还有什么。

## 用标记划出边界，让转账继续

不必让两边约好同一时刻停机。发起者先保存自己的本地状态，再往每条出站通道发送一个特殊的**标记**。对每条通道，标记必须排在保存状态之后发出的任何业务消息前面。此后业务可以照常进行。

一个进程第一次收到本轮标记时，如果尚未保存本地状态，就在处理下一条业务消息前保存，并按同样的规则向外发送标记。触发这次保存的入站通道记为空：排在标记前的消息已经收到，排在标记后的消息不属于发送方保存前的那段历史。

其余入站通道要各记各的。从本地保存状态开始，接收端一边正常处理业务，一边把这些通道上收到的消息按顺序抄入快照。哪条通道的标记到达，就结束哪一条的记录。发起者自己也是如此：它主动保存时还没收到任何标记，所以起初要记录所有入站通道。

## 顺着两笔转账走一遍

起初 A 有 40 枚，B 有 60 枚，两条通道都是空的。下面是一次允许的事件顺序。标记和业务消息走同一条有序通道，所以后发的消息不能超越同方向的标记。

| 事件 | 正在运行的 A、B 余额 | 这一步留下的快照记录 |
| --- | --- | --- |
| A 发起快照，向 B 发送标记 | 40，60 | 保存 A = 40，开始记录 B → A |
| A 向 B 转 4 枚 | 36，60 | 这笔发送在 A 的边界之后 |
| B 尚未收到标记，向 A 转 7 枚 | 36，53 | 这笔发送会被 B 稍后保存的状态包含 |
| B 收到 A 的标记，保存状态，向 A 回送标记 | 36，53 | 保存 B = 53，A → B 记为空 |
| A 收到 7 枚 | 43，53 | A 正常入账，同时把这条消息抄入 B → A 的快照 |
| A 收到 B 的标记；随后 B 收到 4 枚 | 43，57 | B → A 停止记录，已保存的两份余额都不再改动 |

现在按快照对账：A 的 40，加 B 的 53，加 B → A 通道里的 7，正好是 100。恢复这个模型时从 40 和 53 开始，把记录中的 7 枚交付给 A，结果是 47 和 53。不能把运行结束时的 A = 43 拿来再加 7，那会把实时余额与旧快照混用。另一笔 4 枚既不在通道记录里，也没有从快照中的 A 扣除，因为它的发送和接收都在各自边界之后。

有意思的是，这次实际运行里，A = 40 和 B = 53 **从未同时出现**。A 先降到了 36，B 才扣掉那 7 枚。但 B 发送 7 枚并不依赖 A 发送 4 枚。把这两个独立事件的顺序换一换，就能先到达“A 有 40、B 有 53、路上有 7”的状态。快照保证的是这样一个因果上可达的状态，不是一张带有统一拍摄时刻的照片。

## 为什么标记不能走会超车的通道

再看 B → A：B 在保存前发送的 7 枚排在标记前，一定会先到达 A。若它在 A 保存前到达，就已计入 A 的余额；若在 A 保存后到达，就会被抄入通道记录。这两种情况恰好覆盖所有可能，而且不会重复。反过来，B 保存后才发送的消息排在标记后，A 收到它时必然已经保存过状态，也已结束这条通道的记录。这样便排除了表格里“只收未发”的那一行。

假如把标记放到一条更快的控制连接，让它越过那 7 枚，A 就会提前结束记录。随后到达的 7 枚既不在 A 的旧余额里，也不在恢复用的通道里，快照真的只剩 93。控制连接和数据连接即使**各自**可靠有序，也不能保证两个连接合在一起仍然有序。要沿用这里的证明，标记必须和它所划分的数据共享顺序，或者由上层协议提供等价的顺序保证。

每个参与者记录了本地状态、收齐所有入站通道的标记，本地那一份才算完成。整轮要完成，还需要标记能传播到所有参与进程，并最终被接收处理。至于如何持久化这些记录、故障后如何重放输入、怎样避免重复执行外部付款，都需要额外协议。快照在这里给出的，是恢复所必需的那条界线：哪笔转账已经到账，哪笔应该交付，哪笔在这段历史里还没有发生。
