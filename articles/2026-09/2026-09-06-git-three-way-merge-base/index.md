合并两个分支时，只比较末端文件，无法区分某个差异是谁引入的。假设一边的超时值是 `20`，另一边是 `30`：如果共同基线是 `20`，通常应接受后者；如果共同基线是 `10`，则是双方都改了同一设置，需要判断两项改动能否兼容。

Git 的三方合并因此使用 Merge Base、当前分支末端（Ours）和待合并分支末端（Theirs）。它比较两边相对基线的净变化，并不逐个重演历史提交，也不能替开发者理解业务意图。

## 共同祖先提供变化方向

| Merge Base | Ours | Theirs | 单行文本的合并判断 |
| --- | --- | --- | --- |
| `10` | `30` | `10` | 只有 Ours 改动，采用 `30` |
| `10` | `10` | `30` | 只有 Theirs 改动，采用 `30` |
| `10` | `30` | `30` | 双方结果相同，采用 `30` |
| `10` | `20` | `30` | 双方修改同一区域，可能冲突 |

Merge Base 是两个提交之间“尽可能好的共同祖先”。如果一个共同祖先本身是另一个共同祖先的祖先，那么后者更适合作为基线。

```bash
git merge-base main feature
```

该命令输出两者的一个最佳共同祖先；复杂的交叉合并历史可能存在多个最佳共同祖先，可用 `--all` 查看。以上语义来自 [Git 官方 merge-base 文档](https://git-scm.com/docs/git-merge-base)。

在复杂交叉合并历史里，一个“最佳”共同祖先不一定唯一。Git 的 `ort` 策略会在需要时合并多个共同祖先的树，构造三方合并参考树；因此 Merge Base 不能简单等同于某个固定的“创建分支时间点”。[Git 合并策略](https://git-scm.com/docs/merge-strategies)

## 三方合并与快进的区别

历史如下：

```text
A---B---C  main
     \
      D---E  feature
```

`B` 是 Merge Base：

```bash
git merge-base main feature
# 输出 B 的提交哈希
```

如果 `main` 修改 `config.yml`，而 `feature` 新增 `PaymentService.java`，两组变化通常可以自动组合。

如果双方都以不兼容方式修改 `config.yml` 的同一区域，Git 无法仅凭历史确定最终意图，因而报告冲突。

若 `main` 没有在 `B` 之后产生新提交：

```text
A---B  main
     \
      D---E  feature
```

`main` 是 `feature` 的祖先，Git 通常只需把 `main` 指针前移到 `E`，即 fast-forward，无须创建新的合并提交。[Git 官方 merge 文档](https://git-scm.com/docs/git-merge)

普通合并会组合双方相对基线的变化，并在必要时创建具有两个父提交的合并提交。快进只移动目标分支指针，因为待合并历史已经包含目标分支；它没有额外的三方内容组合，也不会新建合并提交。`--no-ff` 等策略选项可以要求不同的历史形状，不能只看文件结果判断是哪一种过程。

## 回退过的修改为什么可能再次出现

如果两个分支都把 `timeout = 10` 改为 `30`，其中一边后来又改回 `10`，三方合并看到的是：

```text
Base:   10
Ours:   10  // 修改后又恢复，净变化为零
Theirs: 30
```

结果通常会采用 `30`。合并算法不会把 Ours 中的那次恢复提交自动解释为“禁止这个改动再次出现”；相对共同基线，它只是没有净变化。这是只比较三个树状态的直接结果。[Git：三方合并中的 reverted change](https://git-scm.com/docs/merge-strategies)

若恢复操作承载了业务决定，审查者仍需确认另一分支是否再次引入了被否定的行为。没有文本冲突，只能说明变化能在文本层面组合。

## 用基线解释差异，再处理冲突

查看功能分支相对共同基线的变化，可以执行：

```bash
git diff main...feature
```

这里的三点是有方向的：比较 Merge Base 与右侧 `feature`，并不等同于两边末端的直接比较。后者可写成 `git diff main feature`。要审查 Ours 自己的变化，可以交换参数，但不能把两个结果当作同一个范围。[git diff：三点比较](https://git-scm.com/docs/git-diff)

判断一个提交是否已包含在另一个提交的历史中，可以使用：

```bash
git merge-base --is-ancestor main feature
```

退出码 `0` 表示成立，`1` 表示不成立，其他非零值表示命令失败。自动化脚本应区分“不为祖先”与无效引用等执行错误。

发生冲突后，Ours 指普通 `git merge` 中当前检出的分支，Theirs 指正在合入的分支，名称与 `main`、`dev` 无关。应逐项检查双方对基线做了什么，再决定如何组合，不能机械选择某一侧。`rebase` 等操作对两侧的上下文另有含义，不能照搬这里的称呼。

合并前还应保护未提交修改；复杂脏工作区可能使冲突后的恢复变得困难。完成文本处理后，仍需运行对应行为的验证，因为两个分支修改不同文件也可能共同破坏 API 或业务不变量。
