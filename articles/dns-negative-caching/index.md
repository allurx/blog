刚创建一条 DNS 记录，权威服务器已经能回答，某个递归解析器却仍说查不到。这个现象不一定是记录没有保存：在创建之前，解析器可能已经缓存了一个否定答案。反过来，遇到 `SERVFAIL` 时，单纯等待那条新记录的 TTL，也未必能解释恢复时间。

要判断该等什么、查哪里，先区分缓存保存的究竟是哪一种结论：名称不存在、指定类型的数据不存在，还是本次解析没能完成。本文讨论 DNS 协议中的这些区别，以 RFC 2308 及其更新 RFC 8020、RFC 9520 为依据。例子是按规范推导的简化场景，不是某款解析器的实测输出，也不代表它的默认配置。

## 查不到地址，有三种不同含义

应用通常把域名交给递归解析器，由解析器查询掌握区域数据的权威服务器。查询中不只有名称，还有记录类型和类别。例如，`www.example. IN AAAA` 问的是这个名称的 IPv6 地址记录，其中 `IN` 是 Internet 类别。下面统一使用 `IN`，并先排除别名和通配符，便于看清结果的差异。

| 结果 | 表达的结论 | 不能据此推出什么 |
| --- | --- | --- |
| `NXDOMAIN` | 被否定的名称不存在 | 它的父域和兄弟名称也不存在 |
| `NODATA` | 名称存在，但没有所问类型的数据 | 该名称的其他类型也不存在 |
| `SERVFAIL` | 服务器未能完成这次查询 | 名称不存在，或某种记录一定不存在 |

`NXDOMAIN` 和 `SERVFAIL` 是 DNS 报文中的响应码（RCODE）。`NODATA` 则是对响应内容的归类，没有一个同名的报文响应码。它的响应码为 `NOERROR`，但 Answer 部分没有所问类型的答案。判断时还要看 Authority 部分，因为告诉解析器“继续去问下级服务器”的转介响应，也可能没有最终答案。[RFC 9499 §3](https://www.rfc-editor.org/rfc/rfc9499.html#section-3)

假设 `www.example.` 只有 A 记录。查询 AAAA 得到 NODATA，随后查询 A 仍可能取得 IPv4 地址。若程序把第一次结果保存为“这个域名不存在”，就把只适用于 AAAA 的结论扩大到了整个名称。

同样，权威服务器不可达、委派配置有问题或 DNSSEC 对 DNS 数据的真实性、完整性校验失败，都可能导致解析失败。收到 SERVFAIL 后，应该调查失败原因，而不能据此删除业务中的域名配置。

## 否定答案也有有效期

正向答案可以随记录携带 TTL。NXDOMAIN 和 NODATA 没有所问的记录可供附带 TTL，因而借助 Authority 部分的 SOA 记录表达负缓存有效期。SOA 是区域的管理记录，包含序列号、定时参数等字段。

按 [RFC 2308 §3—§6](https://www.rfc-editor.org/rfc/rfc2308.html#section-3)，权威服务器生成这类否定答案时，使用以下两者的较小值作为 SOA 在响应中的 TTL：

```text
负缓存 TTL = min(SOA 记录自身的 TTL, SOA.MINIMUM)
```

`SOA.MINIMUM` 是 SOA 数据中的一个字段，不是新建 A 或 AAAA 记录上的 TTL，也不应理解为区域内所有记录 TTL 的统一下限。递归解析器转发缓存中的否定答案时，要扣除已经消耗的时间。缺少 SOA 的这类否定响应，按该规范不应缓存（SHOULD NOT）。

例如，某区域 SOA 自身的 TTL 为 900 秒，MINIMUM 为 300 秒。在忽略额外缓存上限、提前淘汰及其他缓存层，也未采用提供过期数据策略的简化条件下：

| 时刻 | 发生的事情 | 同一递归解析器掌握的信息 |
| --- | --- | --- |
| 10:00:00 | 查询尚不存在的 `new.example.`，得到 NXDOMAIN | 可在 300 秒内复用否定答案 |
| 10:01:00 | 管理员创建 `new.example.` 的 A 记录，TTL 为 60 秒 | 已有负缓存不会因这次写入自动消失 |
| 10:02:00 | 再次向这个解析器查询 | 仍可能得到 NXDOMAIN，剩余约 180 秒 |
| 10:05:00 后 | 普通负缓存有效期结束，再次查询 | 需要重新取得可用答案，才可能看到新记录 |

这里的 60 秒作用于取得后的 A 记录，不能倒过来缩短先前缓存的 300 秒否定答案。类似地，后来降低权威侧的负缓存 TTL，也不能直接改写其他解析器已经保存的有效期。

这解释了一个常见误判：向权威服务器查询成功，只能说明它此时拥有记录。另一个解析器还持有旧的否定答案，两者可以同时成立。TTL 到期也只是允许重新查询，并不保证网络和其他配置问题已经消失。

## 缓存的范围取决于答案否定了什么

对于没有别名的简单查询，NXDOMAIN 的复用范围以名称和类别为基础，NODATA 还必须区分查询类型。这是 [RFC 2308 §5](https://www.rfc-editor.org/rfc/rfc2308.html#section-5) 中两种缓存键不同的原因：前者否定名称，后者只否定该名称上的某类记录。

名称还具有树形关系。[RFC 8020 §2](https://www.rfc-editor.org/rfc/rfc8020.html#section-2) 建议递归缓存解析器利用 NXDOMAIN cut：已知 `missing.example.` 不存在时，在负缓存有效期内，可直接否定 `a.missing.example.`，省去继续向上游查询。这个推断只向下延伸，不能用来否定 `other.example.`。

两个边界尤其容易混淆。第一，如果 `leaf.branch.example.` 存在，那么即使 `branch.example.` 本身没有记录，它仍是树上存在的空非终端节点。查询这个节点上的 A 记录应得到 NODATA，不能错误地返回 NXDOMAIN 并否定整棵子树。

第二，答案含有别名链时，必须确认被否定的是哪个名称。例如：

```text
alias.example.  CNAME  missing.example.
missing.example. 不存在
```

查询别名最终得到 NXDOMAIN，不表示 `alias.example.` 这个别名也不存在。负缓存应对应被否定的目标名称。RFC 8020 还允许解析器在子树已有缓存数据时继续使用它直到其 TTL 到期，并允许验证型解析器只对经过 DNSSEC 验证的否定答案实施 cut。因此，不能把这项建议写成所有解析器都必然表现一致的实现保证。

## SERVFAIL 的缓存是在抑制重复失败

名称不存在是一条可以复用的数据结论。解析失败则表示暂时没能获得有用结果。若每个客户端请求都让解析器从头重复失败的上游查询，故障期间的请求负担会继续累积。

[RFC 9520 §2、§3.2](https://www.rfc-editor.org/rfc/rfc9520.html#section-3.2) 更新了 RFC 2308 的要求：解析器必须实现解析失败缓存，缓存时间至少 1 秒、不得超过 5 分钟，匹配到尚未过期的失败条目时不得再次发送相应上游查询。持续失败时应采用退避。具体缓存键和不同失败条件的处理由实现决定，不能一律套用名称负缓存的 SOA 公式。

这也不等于向任意一台服务器查询失败，就立即判定整个解析过程失败。如果其他可用服务器提供了有用答案，查询仍可完成。失败缓存记录的是相应失败条件，SERVFAIL 则是客户端可能看到的响应码，两者不是同一个抽象层次。

假设一个解析器按策略把某次失败保留 20 秒，上游在第 3 秒恢复，后续请求仍可能暂时命中失败缓存。这是按缓存机制推导的恢复延迟，不是规范规定的默认 20 秒。延长缓存能减少无效重试，也会延后对恢复状态的重新探测。

## 排查时先保留完整答案

只记录“DNS 失败”会丢掉最有用的区别。排查时先保留查询名称、类型、使用的解析器、时间以及完整响应，再根据响应选择方向：

- **NXDOMAIN**：确认真正被否定的名称，特别是别名链的末端。比较权威答案和递归答案，检查否定响应中 SOA 的剩余 TTL。
- **NODATA**：确认所问类型。缺少 AAAA 不等于缺少 A，也不等于名称不存在。
- **SERVFAIL**：检查权威服务器可达性、委派和 DNSSEC 等解析条件，并结合解析器的失败缓存配置判断重试时机。

如果响应带有 Extended DNS Error（EDE），它可以提供进一步线索。例如 [RFC 8914 §4.14](https://www.rfc-editor.org/rfc/rfc8914.html#section-4.14) 定义的 `Cached Error`（13）表示服务器从缓存返回 SERVFAIL。EDE 补充错误原因，不改变 RCODE 的处理语义；没有 EDE 也不能据此断言不存在失败缓存。

实际排障还要区分递归解析器、操作系统和应用自己的缓存。清除其中一层，并不能证明其他层也已更新。本文的时间线描述普通 DNS 缓存有效期，不涵盖 [RFC 8767 的 serve-stale](https://www.rfc-editor.org/rfc/rfc8767.html#section-4) 等提供过期数据的策略，也不把应用运行时的失败缓存当作 DNS 协议 TTL。

因此，新增记录后仍查不到时，真正要追踪的是此前保存了什么结论、它作用于哪个名称和类型、目前还剩多久。先回答这三个问题，才能判断应该等待负缓存失效、修正记录类型，还是继续处理解析故障。
