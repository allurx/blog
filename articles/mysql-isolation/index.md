从账户 A 向账户 B 转 20 元，需要扣款和入账两次更新。如果扣款成功、入账失败，钱就少了；如果两次更新都成功，却把金额写成了 200，钱虽然没有凭空消失，转账仍然错了。把操作放进事务能解决第一类问题，第二类问题还需要正确的业务规则。

ACID 把这些要求分成四个方面：操作能否一起提交、数据是否满足约束、并发事务怎样相互影响，以及提交后能否经受故障。它们相互配合，但每一项都有自己的职责。

本文以 **MySQL Community Server 9.7.2、InnoDB** 为基线，解释事务模型与隔离级别。文中的金额和时序用于推导行为，不是并发压测或故障恢复实测。其他存储引擎与持久化配置的保障需要分别核对。[InnoDB 与 ACID](https://dev.mysql.com/doc/refman/9.7/en/mysql-acid.html)

## 一次转账需要哪些保证

### 原子性：扣款和入账形成一个提交单位

假设转账前 A 有 100 元、B 有 50 元，目标是 A 变为 80 元、B 变为 70 元。两次更新应放在同一个事务中；成功时一起提交，失败时回滚这次事务里的变更。

原子性回答的是这些修改最终作为哪个单位提交或撤销。它还没有回答另一个连接在转账过程中能看见什么，那是隔离性的范围。例如允许读取未提交数据的隔离级别，会让观察者接触到尚未成为最终结果的值。

### 一致性：提交后的数据仍满足业务约束

这次不含手续费的转账应保持余额总和为 150 元，同时扣款金额必须合法，余额不能违反系统的透支规则。数据库可以用唯一键、外键等约束检查部分要求；业务含义则需要应用和数据库设计共同表达。

如果程序原子地执行了“A 减 20、B 加 200”，数据库仍可能成功提交。事务把错误操作一起保存了，一致性却没有得到满足。因此，使用事务的前提仍然是操作本身正确，并且关键约束在并发条件下也能成立。

### 隔离性：另一个事务怎样参与这段过程

转账期间，另一个事务可能在查询余额，也可能在从 A 扣款。InnoDB 通过锁和多版本并发控制（MVCC）协调这些操作：有些查询读取可见的历史版本，有些查询申请锁并等待其他写入完成。

所以，讨论隔离性时要同时写出查询方式和执行时序。只说“这个方法开启了事务”，无法确定另一个连接能读到哪个余额，也无法证明先读后改不会使用过期信息。

### 持久性：确认提交之后，结果能承受什么故障

客户端收到提交成功后，希望服务器重启仍能恢复这次转账。InnoDB 的 redo log、提交刷盘策略、操作系统和存储设备共同参与这项保证。启用 binlog 时，还要考虑 `sync_binlog`。

doublewrite buffer 主要应对数据页的部分写入，它不能单独代替提交日志与刷盘要求。为了降低写入开销而调整持久化配置，可能改变故障后丢失已确认事务的范围；这项取舍需要与业务对数据丢失的容忍度一致。

## 用余额查询理解三种并发现象

现在暂时不做转账，只看账户 A 的查询。以下现象描述的是另一个事务的修改如何进入当前事务的观察：

| 现象 | 一个具体时序 | 风险 |
| --- | --- | --- |
| 脏读 | B 把余额改为 80，A 读到 80，随后 B 回滚 | A 依据了一次最终未成立的修改 |
| 不可重复读 | A 先读到 100，B 修改为 80 并提交，A 再读到 80 | 同一事务前后读到同一行的不同值 |
| 幻读 | A 查询余额大于 0 的账户，B 改变符合条件的记录并提交，A 再查时结果集合变化 | 前后判断基于不同的行集合 |

不可重复读关注同一行的值，幻读关注条件对应的行集合。这些定义便于描述现象，但实现分析还需要区分普通 SELECT、锁定读和 UPDATE。尤其在 InnoDB 中，不能把一个通用隔离级别对照表直接套到所有语句上。

## InnoDB 的四个隔离级别

### 普通读取在哪个时刻取得快照

| 隔离级别 | 普通读取的主要语义 |
| --- | --- |
| READ UNCOMMITTED | 可以读取其他事务未提交的数据，允许脏读 |
| READ COMMITTED | 每次一致性读取得新的快照，因此两次查询之间可能看到别人刚提交的修改 |
| REPEATABLE READ | 默认级别；同一事务的普通一致性读通常沿用首次建立的快照 |
| SERIALIZABLE | 在相应条件下把普通读取转换为加锁读取，提供更强隔离，也可能增加阻塞 |

继续使用表中的第二个时序：A 首次读到 100，B 把余额改成 80 并提交。A 没有自行修改该记录时，READ COMMITTED 下的下一次普通查询使用新快照，可以读到 80；REPEATABLE READ 下的普通一致性读仍可读到 100。差异来自快照建立时机。

SERIALIZABLE 也不是按事务开始时间把所有事务排成一条队列。实际的阻塞与放行依赖语句、锁和提交时序。[MySQL 隔离级别说明](https://dev.mysql.com/doc/refman/9.7/en/innodb-transaction-isolation-levels.html)

### 锁定读遵循另一套访问规则

`SELECT ... FOR UPDATE` 用于读取并保护准备操作的数据。它不会简单地取得普通 SELECT 的旧快照，然后给那个历史值补一把锁。因此，同一个 REPEATABLE READ 事务中，两种读取可能得到不同值。

对范围查询，InnoDB 还可能用 next-key locks 限制范围内插入；实际范围由索引、扫描条件和隔离级别共同决定。这解释了为什么“REPEATABLE READ 是否有幻读”需要先明确语句和时序。具体的两连接示例见[普通 SELECT 与 SELECT FOR UPDATE 的版本差异](/innodb-consistent-reads/)。

## 分析实际事务时，从 SQL 和连接状态开始

在 MySQL 客户端或连接工具中，先查看真正运行查询的服务端和会话状态：

```sql
SELECT VERSION(), @@version_comment,
       @@SESSION.transaction_isolation, @@SESSION.autocommit;
```

然后把一次业务操作展开为两个连接的时间线：何时开始事务、何时查询、何时加锁或更新、何时提交。表结构、索引和存储引擎也要一起保留，否则相同的 WHERE 条件未必意味着相同的锁范围。

对于开篇的转账，至少要回答三个具体问题：两次余额修改是否属于同一事务，金额与余额约束在哪里检查，并发扣款能否绕过这些检查。提高隔离级别有时会改变第二、三个问题的实现条件，但无法把两个各自已经提交的操作重新变成一个事务。
