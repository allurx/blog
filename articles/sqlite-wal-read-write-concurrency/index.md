SQLite 常被概括为“单文件数据库”，这很容易让人以为读取和写入必须轮流独占同一个文件。在默认的回滚日志模式中，写入数据库文件的关键阶段确实需要暂时排除读者；启用 Write-Ahead Logging（WAL）后，读事务却可以在另一个连接提交写事务时继续运行。

关键不在于 SQLite 取消了锁，而在于它把“读者正在查看的旧版本”和“写者正在追加的新版本”放在不同位置。每个读事务再用一个固定的 WAL 边界选择自己的快照。本文沿一次读写交错解释这套机制，并说明它没有解决的三个限制：同时仍只有一个写者，长读事务会阻碍检查点，旧读快照也不能直接升级为写事务。

## 回滚日志模式会修改主数据库

SQLite 的回滚日志模式先把待修改页面的原内容写入单独的 journal，再原地更新主数据库文件。journal 用于回滚和崩溃恢复，但读者取得页面时最终仍要面对正在被改写的主文件。

为了不让其他连接看到一半旧、一半新的页面状态，写事务在真正修改主数据库时必须取得排他访问。已有读者需要先退出，新读者也要等待写入完成。[SQLite 的隔离说明](https://www.sqlite.org/isolation.html#isolation_and_concurrency)把这种行为概括为：回滚模式通过暂时将读者排除在外，保证它们不会观察到未完成的事务。

这套设计可以提供隔离，却让读与写在落盘阶段争用同一份内容。WAL 改变的正是页面新版本的落点。

## 写者追加 WAL，读者保留自己的边界

启用 `PRAGMA journal_mode=WAL` 后，已提交的旧页面继续留在主数据库文件中。写事务把页面的新版本追加到 `-wal` 文件末尾，并以一个 commit record 标记事务提交；提交不要求立刻覆盖主数据库。SQLite 官方文档将这种反转称为 [Write-Ahead Logging](https://www.sqlite.org/wal.html#how_wal_works)。

读事务开始时会记住当时 WAL 中最后一个有效 commit record 的位置，文档称其为 *end mark*。在这个事务存续期间，end mark 不再改变。读取页号 $P$ 时，读者按以下顺序找值：

1. 在自己的 end mark 之前查找页 $P$ 的最后一个有效版本；
2. 如果 WAL 的这段范围没有该页，就从主数据库文件读取；
3. 忽略 end mark 之后新追加的所有内容。

WAL 中同一页可能出现多次。读者需要的是不越过自己边界的最新版本，而不是文件中绝对位置最后的版本。实际查找由共享内存中的 `-shm` 文件维护的 *wal-index* 加速，不必每次线性扫描整个 WAL。[SQLite 的 WAL 并发算法](https://www.sqlite.org/wal.html#concurrency)也因此要求参与者位于同一台机器；依赖共享内存的 WAL 不适合直接放在网络文件系统上由多台主机共同访问。

## 两个连接可以看到不同快照

假设表中 `counter.value` 初始为 10，连接 X 和 Y 按下面的顺序运行：

| 时刻 | 连接 X                                             | 连接 Y                                                    | X 看到的值 |
| ---- | -------------------------------------------------- | --------------------------------------------------------- | ---------- |
| 1    | `BEGIN; SELECT value FROM counter WHERE id = 1;`   |                                                           | 10         |
| 2    |                                                    | `UPDATE counter SET value = 11 WHERE id = 1; COMMIT;`     |            |
| 3    | `SELECT value FROM counter WHERE id = 1;`          |                                                           | 10         |
| 4    | `COMMIT; BEGIN; SELECT value FROM counter WHERE id = 1;` |                                                     | 11         |

X 在时刻 1 固定了自己的 end mark。Y 在时刻 2 把新页面和提交记录追加到这个边界之后，不需要覆盖 X 可能正在读取的旧页面，所以两者可以并行。X 的第二次查询仍忽略新提交，维持同一快照；结束旧读事务并开始新事务后，它才取得包含 Y 提交的新边界。

这就是 WAL 模式下的[快照隔离](https://www.sqlite.org/isolation.html#isolation_and_concurrency)。不同读者可以在不同时间开始，因而持有不同的 end mark，同时看到数据库的不同历史版本。写者追加新版本不会改变已经发放的读快照。

## 检查点合并页面，但不能越过最老读者

新版本不能永远只留在 WAL。SQLite 通过 *checkpoint* 把已提交页面复制回主数据库，并在条件允许时重用 WAL。默认配置通常在 WAL 达到 1000 页左右时自动尝试检查点，也可以由应用主动触发。

检查点可以和读者同时运行，但它不能把某个活跃读者仍依赖的状态覆盖掉。设当前读者中最早的 end mark 为 $E$，检查点最多安全推进到 $E$；越过这个位置写回主数据库，可能让该读者从主文件取得属于未来快照的页面。SQLite 会记住已推进的位置，等后续检查点继续工作。

因此，“读者不阻塞写者”不等于读者没有任何系统影响。一个长期不结束的旧读事务会让检查点无法完全推进和重置 WAL。若活跃读者不断重叠，始终没有空档，可能发生 *checkpoint starvation*：写者仍能追加，WAL 却持续增长，读取查找和磁盘占用随之变差。[SQLite 的检查点说明](https://www.sqlite.org/wal.html#checkpointing)建议控制读事务长度，并根据工作负载调整自动或主动检查点策略。

## WAL 仍然把写事务串行化

所有写者都要向同一个 WAL 追加并更新协调状态，所以 SQLite 同一时刻仍只允许一个写事务。WAL 提供的是“一位写者与多位读者并行”，不是多写者同时提交。[SQLite 事务文档](https://www.sqlite.org/lang_transaction.html#read_transactions_versus_write_transactions)明确区分了多个并发读事务和单个写事务。

这也解释了为什么长写事务仍然昂贵。写者在事务中等待网络、处理大量业务逻辑或逐条执行慢操作时，会长期占有写入位置，让其他写连接收到 `SQLITE_BUSY` 或等待 busy handler。WAL 只能避免写者为了提交新页面而排除普通读者，不能消除写者之间的串行约束。

`BEGIN IMMEDIATE` 会在事务开始时就尝试取得写事务，而不是先建立读快照、到第一条写语句时再升级。它适合明确知道随后需要写入的场景，但成功后也会阻止其他写者开始；它不是提高写并行度的开关。

## 旧读快照不能原地变成新写分支

读写并发还有一个容易忽略的边界。连接 X 持有旧快照时，连接 Y 可以提交新版本；若 X 随后直接执行 `UPDATE`，SQLite 不能让它基于过时状态创建另一条历史分支。这个升级会以扩展错误码 `SQLITE_BUSY_SNAPSHOT` 失败。

[SQLite 对该错误的定义](https://www.sqlite.org/rescode.html#busy_snapshot)给出的恢复方式是结束旧读事务，再从最新状态开始一个新事务。若业务从一开始就确定需要读取后写入，可以考虑 `BEGIN IMMEDIATE` 提前竞争写者位置。无论采用哪种方式，应用都应把 `SQLITE_BUSY` 类错误当作并发结果处理，而不是假设 WAL 会让任何事务组合自动成功。

## 并发来自版本分离，不是锁消失

WAL 模式让写者把新页面追加到日志，让读者用固定 end mark 组合主数据库与 WAL 中的旧版本。页面存放位置的分离避免了普通读事务和提交写事务互相排除，固定边界则保证每个读事务始终看到一致快照。

这套机制的代价也从同一结构中产生：写者仍必须串行，检查点受最老读快照限制，过时快照不能升级为新的写分支。理解 end mark、追加写和检查点三者的关系，比简单记住“WAL 更并发”更有用，也能直接指导事务时长、重试策略与检查点配置。
