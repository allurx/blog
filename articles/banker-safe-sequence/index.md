资源池还剩一个空闲单元，某个任务恰好申请一个，直接分给它似乎没有问题。但任务拿到这个单元之后，可能还要申请另一个才能完成。如果其他任务也握着资源等待追加分配，眼前这次合法的分配就可能堵住所有人的退路。

银行家算法关心的正是这种情况：批准请求之后，系统是否仍保留一种让所有任务完成并归还资源的办法。本文从一个两类资源的例子解释安全性检查，不涉及特定操作系统实现。只需理解资源借出、归还和整数向量的逐项比较。

## 最大需求是一份承诺

算法先要求每个任务声明执行期间可能同时占用的资源上限。这里的“最大需求”不是累计申请次数，也不是下一次请求量。一个任务可以反复借还，但任意时刻的持有量不能超过声明。

模型还要求同一类别的资源单元可以互换，资源总量固定，任务取得所需资源并得到执行机会后能在有限时间内完成，完成时归还全部持有资源。资源申请统一经过分配器；未纳入模型的锁、外部消息依赖和故障不在这个保证之内。Dijkstra 的[原始论述 EWD623](https://www.cs.utexas.edu/~EWD/ewd06xx/EWD623.PDF)用单类资源描述这些约束，并把分配决策建立在分配后仍然安全的条件上。

对多类资源，用四组量表示当前状态：

| 名称 | 含义 |
| --- | --- |
| `Total` | 每类资源的总数 |
| `Available` | 每类资源目前尚未借出的数量 |
| `Allocation[i]` | 任务 i 当前持有的数量 |
| `Max[i]` | 任务 i 声明的同时持有量上限 |

由它们得到剩余需求上界 `Need[i] = Max[i] - Allocation[i]`。所有减法和比较均逐分量进行，例如 `(1, 2) ≤ (2, 1)` 不成立：第二类资源不足，第一类的富余不能抵消它。

下面设资源 X、Y 各有 3 个，三个任务的状态如下。这是用于推导的完整小例子，数对依次表示 X 和 Y 的数量。

| 任务 | Allocation | Max | Need |
| --- | --- | --- | --- |
| A | (1, 0) | (2, 1) | (1, 1) |
| B | (0, 1) | (1, 2) | (1, 1) |
| C | (1, 1) | (3, 2) | (2, 1) |

已分配总量是 `(2, 2)`，所以 `Available = (1, 1)`。注意所有 `Max` 相加得到 `(6, 5)`，大于资源总量。这并不自动意味着过量承诺，因为任务可以先后完成，后面的任务复用前面归还的资源。

## 用归还链证明安全

先不实际分配，复制空闲资源向量，记为 `Work`。假如某个任务的全部剩余需求都能被 `Work` 满足，就可以设想先让它取得所需资源、完成并归还持有量，再考虑下一个任务。

对上面的状态，可以按 A、B、C 的顺序进行这种模拟：

| 模拟完成的任务 | 完成前 Work | 该任务 Need | 完成后 Work |
| --- | --- | --- | --- |
| A | (1, 1) | (1, 1) | (2, 1) |
| B | (2, 1) | (1, 1) | (2, 2) |
| C | (2, 2) | (2, 1) | (3, 3) |

每一步的 `Need` 都不超过当时的 `Work`。因此，即使三个任务都要用足声明的额度，也能沿这条归还链完成。A、B、C 就是一个安全序列，当前状态是安全状态。

完成后为什么只加回 `Allocation[i]`，不加 `Max[i]`？因为模拟中补给任务的 `Need[i]` 也来自 `Work`，先借出再归还，净变化抵消了：

$$
Work' = Work - Need_i + (Allocation_i + Need_i)
      = Work + Allocation_i
$$

漏掉借出这一步却加回 `Max`，会凭空制造资源。例如模拟 A 完成时若算成 `(1, 1) + (2, 1) = (3, 2)`，就已经比实际多出了 `(1, 1)`。

安全序列是可完成性的证明，不要求调度器真的把全部任务串行执行。[Cornell 的死锁避免讲义](https://www.cs.cornell.edu/courses/cs4410/2015su/lectures/lec11-deadlock2.html)也以这样的完成序列定义安全状态。实际执行可以交错，只要每次批准请求后都保留安全性。

## 同一个请求，给谁结果不同

现在 C 申请 `(1, 0)`。它没有超出 `Need[C] = (2, 1)`，现有空闲量 `(1, 1)` 也足够。若只检查这两个条件，请求就会获批。

试着在副本上批准后，状态变成：

- `Available = (0, 1)`；
- `Allocation[C] = (2, 1)`；
- `Need[C] = (1, 1)`，A、B 的 Need 仍各为 `(1, 1)`。

此时每个任务都可能再要一个 X 才肯归还已有资源，而池里已经没有 X。安全性模拟连第一个可保证完成的任务也找不到。银行家算法因此让 C 等待，真实分配状态保持不变。

如果同样的 `(1, 0)` 改由 A 申请，结果却不同。试分配之后，空闲量仍是 `(0, 1)`，但 A 的持有量成为 `(2, 0)`，剩余需求降为 `(0, 1)`。于是可以先让 A 完成，空闲量回升到 `(2, 1)`；再让 B 完成，得到 `(2, 2)`；最后 C 完成，得到 `(3, 3)`。这次请求可以批准。

两次请求消耗的资源完全一样，区别在于它们是否把某个任务推进到了“可以完成并归还”的位置。空闲资源数只是检查的输入，资源在任务之间的分布同样决定是否安全。

## 为什么不用枚举所有排列

安全性检查的伪代码可以很短。下面假设各向量长度一致、数量非负、持有量不超过上限，且资源守恒；`≤` 仍表示逐分量比较。

```text
Work = copy(Available)
Remaining = 所有任务
Sequence = 空序列

while Remaining 非空:
    找一个 i 属于 Remaining，使 Need[i] ≤ Work
    若找不到:
        返回“不安全”
    Work = Work + Allocation[i]
    从 Remaining 移除 i
    将 i 追加到 Sequence

返回“安全”和 Sequence
```

一个容易产生的疑问是：随便选一个符合条件的任务，会不会选错顺序，导致后面失败？不会。模拟任务完成只会让 `Work` 的每个分量保持不变或增加，不会消耗掉后续任务赖以完成的资源。

更具体地说，假设原本存在一个安全序列，而现在选中了其中较靠后的任务 i。既然 i 此刻已经能完成，就把它提前到序列开头。原来排在它前面的任务获得了不少于原先的可用资源，仍然可以完成；越过 i 的原位置后，已经归还的资源集合与原序列一致，后续步骤也仍成立。因此任意一个符合条件的选择都不会破坏已有的可行性，不需要回溯试遍排列。

若扫描后剩下的每个任务都有至少一类资源不足，就无法在这些任务中确定第一个保证完成者。它们完全可能同时要求补足自己的剩余额度，再归还任何资源。这个允许出现的需求组合足以否定安全保证。[Yale 的课程笔记](https://www.cs.yale.edu/homes/aspnes/pinewiki/Deadlock.html#6.1._The_Banker.27s_algorithm)给出了对应的多资源矩阵检查方法。

对 n 个任务、m 类资源，直接实现每轮最多检查 n 个任务，最多完成 n 轮，每次比较 m 个分量，时间上界为 `O(n²m)`。这是这段朴素伪代码的上界，不是说算法必须搜索 `n!` 种顺序。

处理实际请求时，还要先检查请求非负且不超过该任务的 `Need`。超过声明属于无效请求；合法但超过 `Available` 的请求需要等待。其余请求在副本上扣减 `Available`、增加 `Allocation`、扣减 `Need`，通过安全性检查后才提交。检查到提交之间也必须防止其他分配改变依据，否则两个请求各自通过检查，并不代表一起提交后仍然安全。

## 不安全不等于已经死锁

C 的试分配状态不安全，但这张表并未告诉我们任务下一步究竟会做什么。如果 A 实际不再需要 X，而是在当前持有量下完成并归还一个 X，其他任务仍可能继续。最大需求只是上界，任务未必会用足。

相反，如果 A、B、C 接下来都请求一个 X，并且都要拿到它才释放已有资源，就会真正陷入等待：X 全在这些任务手中，却没有任何任务能够先完成。算法拒绝试分配，是因为无法保证避开这个未来，而不是已经观察到它发生。

这种保守性带来两项实际代价。需求上限申报得过大，会使本来可能顺利完成的请求被延后；上限无法事先确定，则模型本身就难以建立。即使资源分配状态安全，任务无限循环、不释放资源、等待模型外事件，或者调度器长期不给它执行机会，也不会被这个检查解决。安全性证明不能替代程序的终止条件和公平调度。

因此，使用银行家算法的前提不只是“有一个资源池”，还包括可执行的需求承诺和统一的分配控制。它提供的判断很明确：在这些承诺成立的条件下，每次借出资源后，都应当仍能找到一条最终全部归还的路径。眼前有空闲量，只说明请求付得起；保留这条路径，才说明付出之后还能收得回来。
