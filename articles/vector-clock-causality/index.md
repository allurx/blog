分布式系统里，两条记录都带着时间，并不意味着可以凭时间先后判断谁影响了谁。机器的物理时钟会漂移；即使改用单调递增的逻辑时钟，一个较小的数字也可能只是来自另一个从未通信的进程。

向量时钟（vector clock）记录的不是几点几分，而是每个参与者目前知道各参与者已经推进到哪一步。对两个向量做逐分量比较，便能回答一个更适合分布式系统的问题：一个事件是否可能通过本地执行和消息传递影响另一个事件，还是二者没有可观察的先后关系。

本文使用固定的三个进程 A、B、C，从 `happened-before` 关系推导更新与比较规则。目标不是用向量时钟生成全局流水号，而是理解它如何保留因果偏序，以及为什么“并发”仍不等于“同一物理时刻”。

## 因果关系只要求部分有序

[Lamport 对 `happened-before` 的定义](https://lamport.azurewebsites.net/pubs/time-clocks.pdf)从三条规则开始。记 `e → f`：

1. 若 e、f 属于同一进程，并且 e 在本地顺序中先于 f，则 `e → f`。
2. 若 e 是一条消息的发送，f 是同一条消息的接收，则 `e → f`。
3. 关系可传递：若 `e → f` 且 `f → g`，则 `e → g`。

如果既没有 `e → f`，也没有 `f → e`，就称两个事件**并发**。这里的并发表示系统观察不到由本地顺序和消息建立的因果路径；它不要求事件在物理时间上重叠，也不声称现实世界中绝无其他联系。

标量 Lamport 时钟能保证：

$$
e \rightarrow f \Longrightarrow L(e) < L(f).
$$

反向却不成立。两个互不通信的进程各自执行若干事件，也会得到可以比较的整数；`L(e) < L(f)` 不能据此证明 `e → f`。在时间戳后加进程 ID 可以得到稳定的全序，适合确定排序结果，但人为打破平局不会凭空创造因果关系。

## 一个分量代表一条已知进度

设系统有 N 个身份固定的进程，每个进程保存长度为 N 的非负整数向量，初始全为 0。进程 i 执行事件时使用以下规则：

- **本地或发送事件**：先把自己的分量 `V[i]` 加 1；发送时把更新后的向量附在消息上。
- **接收事件**：先将本地向量与消息向量逐分量取最大值，再把自己的分量加 1。

逐分量最大值不是在选一个“更晚”的时钟，而是在合并两边已经知道的因果历史。随后递增接收方分量，为本次接收事件留下新位置。

下面是一段三进程执行。向量分量始终按 `[A, B, C]` 排列：

| 事件 | 动作 | 向量 |
| --- | --- | --- |
| a1 | A 本地计算 | `[1, 0, 0]` |
| a2 | A 向 B 发送 m1 | `[2, 0, 0]` |
| b1 | B 独立执行 | `[0, 1, 0]` |
| b2 | B 接收 m1 | `[2, 2, 0]` |
| c1 | C 独立执行 | `[0, 0, 1]` |
| b3 | B 向 C 发送 m2 | `[2, 3, 0]` |
| c2 | C 接收 m2 | `[2, 3, 2]` |

b2 的计算过程是 `max([0, 1, 0], [2, 0, 0]) = [2, 1, 0]`，再递增 B 的分量得到 `[2, 2, 0]`。它同时保留了 A 随 m1 带来的进度和 B 在 b1 已经发生的进度。

## 逐分量比较恢复因果偏序

对两个向量 X、Y，定义：

$$
X < Y \iff
(\forall i, X_i \le Y_i) \land
(\exists j, X_j < Y_j).
$$

也就是所有分量都不大于，并且至少一个分量严格小于。在上述模型和更新规则下，向量时钟具有比标量时钟更强的性质：

$$
e \rightarrow f \iff V(e) < V(f).
$$

例如 `V(a1) = [1, 0, 0] < [2, 3, 2] = V(c2)`，对应从 A 本地顺序到 m1、B 本地顺序、m2，再到 C 接收的因果路径。

再比较 a2 与 b1：

- `[2, 0, 0]` 不小于 `[0, 1, 0]`，因为 A 分量 `2 > 0`；
- `[0, 1, 0]` 也不小于 `[2, 0, 0]`，因为 B 分量 `1 > 0`。

两个向量互不可比，所以 a2 与 b1 并发。算法不是“判断谁的数字更大”，而是检查一方掌握的全部进度是否被另一方覆盖。

同目录的[完整 Node.js 示例](./vector-clock.mjs)实现 `tick`、`receive` 和 `compare`，并复现上表：

```sh
node vector-clock.mjs
```

在 Node.js 24.21.0 上的关键输出为：

```text
a1 -> c2: before
a2 vs b1: concurrent
b1 -> b2: before
c1 -> c2: before
```

`compare` 返回 `before`、`after`、`equal` 或 `concurrent`。`equal` 表示两个值携带相同的因果前沿，不足以证明它们是同一个业务对象或同一次事件；身份仍应由独立的事件 ID 或版本 ID 表示。

## 用它识别版本分叉，而不是替你合并数据

向量比较很适合判断副本版本之间的关系。若版本 X 的向量小于 Y，说明 Y 的因果上下文已经包含 X，X 可视为祖先版本。若两者互不可比，则更新发生在彼此都未观察到对方的分支上，系统应保留冲突、交给业务合并，或使用具有明确合并语义的数据类型。

[Amazon Dynamo 论文中的版本演化示例](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)正是这种用法：同一对象的两个并发分支各自携带向量时钟，读取时可识别无法由祖先关系消除的版本，协调后的新写入再覆盖两个分支的因果上下文。

但“检测到并发”并没有给出正确合并策略。购物车或许能合并商品集合，账户余额却不能简单任选一个版本；删除、重复操作和业务不变量也需要单独建模。向量时钟保存关系信息，不理解载荷语义。

## 精确性需要付出元数据成本

经典向量时钟假定参与者集合和身份已知，每个时间戳携带一个分量。N 个参与者意味着 O(N) 的存储与传输成本；成员频繁加入、离开或拥有短暂身份时，向量还会膨胀。删除一个长期不活跃的分量也不能只看墙上时间，否则可能把尚未传播的因果历史一并删除。

实际系统因此常按副本而不是客户端分配身份，限制跟踪范围，或使用 version vector、dotted version vector 等变体。[Riak 的因果上下文文档](https://docs.riak.com/riak/kv/2.2.0/learn/concepts/causal-context/index.html)也区分传统向量时钟与 dotted version vector：二者服务于版本因果跟踪，但后者把引入某个值的具体事件与汇总上下文分开，以更精细地判断哪些兄弟版本已被覆盖。

还有几条边界必须保留：

- 向量时钟不包含物理时间，不能回答延迟、持续时间、过期时间或“最新几点写入”。
- 它给出偏序，不自动产生所有事件都一致的展示顺序；需要全序时仍须额外的确定性规则或共识协议。
- 只有被建模并正确携带时间戳的本地事件和消息才进入因果关系；漏传上下文会让真实依赖在模型中消失。
- 比较结果描述潜在因果路径，不证明前一个事件在业务语义上确实导致后一个事件。

[Mattern 的向量时间论文](https://vs.inf.ethz.ch/publ/papers/VirtTimeGlobStates.pdf)将这种结构描述为部分有序的时钟向量：它保留分布式执行的因果结构，而不是把所有事件压成一条人为时间线。理解这一点，更新规则就不再像记账技巧——每个分量是一条已知进度，逐分量最大值合并知识，偏序比较则把“已经观察到”与“仍可能并发”准确分开。
