把 `cacao` 的字母按大小排列，得到 `aacco`，原来的顺序就丢了。Burrows–Wheeler 变换（BWT）也要排序，却能把 `cacao` 编成 `occ#aa`，再一个字母不差地解回来。区别在于，它排序的是**从不同位置开始读的整串字符**。输出中的每个字符都在回答一个问题：这一行的起点前面是什么？

## 最后一列记下了每一行的前一个字符

先约定 `#` 是专用结束符，不会出现在正文里，并且排在所有字母之前。给原文加上它，得到 `cacao#`。把这六个字符围成一圈，每次换一个起点，沿原方向读满六个字符。按字典序排列这六种读法，行号从 0 开始：

| 行号 | 从该起点读一圈 | 首列 F | 末列 L |
| --- | --- | --- | --- |
| 0 | `#cacao` | `#` | `o` |
| 1 | `acao#c` | `a` | `c` |
| 2 | `ao#cac` | `a` | `c` |
| 3 | `cacao#` | `c` | `#` |
| 4 | `cao#ca` | `c` | `a` |
| 5 | `o#caca` | `o` | `a` |

竖着读末列，就是要保存的 `occ#aa`。例如第 1 行从一个 `a` 开始，读完一圈时最后碰到 `c`，可见原文中这个 `a` 的前一个字符是 `c`。想接着向前读，应当跳到以**这个** `c` 开头的行。表里却有两行都以 `c` 开头。解码时整张表已经丢掉了，怎么知道跳到哪一行？

## 两个 c 不需要编号，但必须按出现次序配对

先找回首列。每个位置都轮过一次当起点，也都轮过一次当末尾，所以首列和末列包含完全相同的一批字符。又因为整行已经按字典序排列，首列只能是末列排好序的结果：`#aacco`。

现在看末列里的两个 `c`。把它们所在行的最后一个字符移到行首，相当于把起点往前挪一格：

- 第 1 行 `acao#c` 变成 `cacao#`，落在第 3 行。
- 第 2 行 `ao#cac` 变成 `cao#ca`，落在第 4 行。

为什么前一行仍然在前？原来的两行尾部都是 `c`，先后取决于前面的 `acao#` 和 `ao#ca`。移位后，两行开头都是 `c`，先后仍然取决于这两段。**同一个字母从末尾移到开头，不改变这一组行的相对顺序。** 因此末列自上而下第一个 `c` 对应首列第一个 `c`，第二个对应第二个。对任何字符都成立。这条从末列位置找到首列位置的规则叫作 LF 映射（last-to-first mapping）。

算一次实际的跳转。末列第 2 行是 `c`，它前面已有一个 `c`。比 `c` 小的字符共有三个：一个 `#`、两个 `a`。所以首列的 `c` 从第 3 行开始，眼前这个要再往后移一位，目标是第 4 行。一般地，若当前字符为 `x`，目标行号就是**全列中比 x 小的字符个数，加上末列当前行之前的 x 个数**。两处都按字符出现的次数计数，第二项不包含当前行。

## 从结束符出发，每次往回走一个字符

首列第 0 行以 `#` 开头，因此这一行的末列就是原文最后一个字母。从这里反复读末列、按 LF 跳转，直到读到结束符：

| 当前行 | 读到的末列字符 | 下一步 |
| --- | --- | --- |
| 0 | `o` | 跳到第 5 行 |
| 5 | `a` | 第二个 `a`，跳到第 2 行 |
| 2 | `c` | 第二个 `c`，跳到第 4 行 |
| 4 | `a` | 第一个 `a`，跳到第 1 行 |
| 1 | `c` | 第一个 `c`，跳到第 3 行 |
| 3 | `#` | 读完 |

依次拿到 `oacac`，反过来便是 `cacao`。这也能检验刚才的配对规则：如果把两个 `c` 的目标对调，从第 2 行就会误跳到第 3 行，提早碰见 `#`。字符一个也没少，走出的原文却只剩 `cao`。重复字符的次序正是解码所需的信息。

表中的旋转串只用来解释原理。实际解码不需要它们：统计各字符的频数，按字母表顺序累加，就能得到每种字符在首列的起始行。再从上往下扫描末列，用计数器记住每种字符已经出现几次，便能为每一行填好 LF。最后按这张行号表回走，把字符从输出缓冲区末端向前填。对固定大小的字节字母表（另加一个结束符），构表和恢复都只需与块长成正比的时间，行号表占线性空间。

## 保留原文起点，不等于已经压缩

结束符解决的是“从圆环哪里剪开”。不加结束符时，`cacao` 和它的旋转串 `acaoc` 会产生完全相同的一组旋转行，末列自然也相同。本文用唯一的 `#` 标出边界；[Burrows 和 Wheeler 的原始报告](https://www.mit.edu/~6.454/www_fall_2002/bwt/burrowswheeler94.pdf)给出的另一种做法，是把原串所在的行号连同末列一起保存。如果输入允许任意字节，就不能随手挑一个可能出现在正文里的字节当专用标记。

那 BWT 对压缩有什么用？看表里的第 1、2 行：两个起点后面的内容都以 `a` 开头，因此排到了一起，而它们前面恰好都是 `c`，末列里就出现了 `cc`。一般情况下，按后续内容排序会把有相同前缀的行聚在一起；如果这些位置前面的字符也常常相同，末列就可能出现连续的重复字符，方便后续编码利用。

这里的“可能”很重要。重排不会减少任何字符，也不保证每块数据都产生长串重复。把 `cacao#` 变成 `occ#aa`，六个字符仍是六个。BWT 保住了还原的路径，同时改变了哪些字符彼此相邻；真正把这种相邻关系换成更少比特的，是后面的编码步骤。
