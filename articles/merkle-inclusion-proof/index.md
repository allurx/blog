假设一批记录已经生成一个公开的根哈希。后来，有人声称 `gamma` 就在这批记录里。直接交付全部记录当然可以验证，但数据量很大时，传输和重新计算整个集合都不划算。

Merkle tree（Merkle 树，也称哈希树）把记录哈希逐层合并成一个根。要验证某个叶子，证明者只需提供从该叶子到根的每一层中缺少的兄弟哈希。验证者沿路径重算，最终结果与可信根一致，就能确认这条记录被承诺在该位置。

本文采用 [RFC 9162 的 Merkle Tree Hash 定义](https://www.rfc-editor.org/rfc/rfc9162.html#section-2.1.1)，先分析四个叶子的完整二叉树，再说明非二次幂叶子数、证明边界和实现细节。示例使用 SHA-256，但结构本身并不限定某一种哈希函数。

## 一个根如何承诺四条记录

设原始记录按顺序为 `alpha、beta、gamma、delta`。先给叶子数据加前缀字节 `0x00`，再计算哈希：

$$
L_i=H(\mathtt{0x00}\mathbin{\|}d_i).
$$

内部节点使用另一个前缀 `0x01`，并严格按左、右顺序拼接两个子哈希：

$$
N=H(\mathtt{0x01}\mathbin{\|}N_{left}\mathbin{\|}N_{right}).
$$

于是四个叶子的根为：

$$
R=H(\mathtt{0x01}\mathbin{\|}
H(\mathtt{0x01}\mathbin{\|}L_0\mathbin{\|}L_1)\mathbin{\|}
H(\mathtt{0x01}\mathbin{\|}L_2\mathbin{\|}L_3)).
$$

叶子和内部节点使用不同前缀，这叫作**域分离**。它让同一串字节在“原始记录”和“两个子节点的拼接”中具有不同含义。RFC 9162 明确要求这种区分，以获得所需的 second preimage resistance。只写成 `H(left || right)`，却不定义叶子编码、节点编码和边界，会让树的安全含义依赖隐含假设。

顺序同样属于承诺的一部分。交换 `alpha` 与 `beta` 会先改变左侧内部节点，随后改变根。这里承诺的是一个**有序记录列表**，不是忽略顺序的集合。重复值也允许存在：两个内容相同的叶子拥有相同叶子哈希，但它们的索引不同。

## 证明 gamma 只需要两个兄弟

`gamma` 位于索引 2。验证者已经拥有原始记录 `gamma`、目标索引、树大小和可信根，不需要证明者重复提供路径上的父节点，因为父节点都能计算出来。

第一层需要 `delta` 的叶子哈希 L₃。它在当前节点右侧，因此先计算：

$$
P=H(\mathtt{0x01}\mathbin{\|}L_2\mathbin{\|}L_3).
$$

第二层需要另一半子树的根，也就是：

$$
Q=H(\mathtt{0x01}\mathbin{\|}L_0\mathbin{\|}L_1).
$$

Q 在 P 左侧，最终计算 `H(0x01 || Q || P)`。若结果等于可信根 R，证明成立。因此，这份包含证明只有两个哈希：`[L₃（右）, Q（左）]`。

方向不能省略。密码学哈希不满足交换律，通常有 `H(A || B) ≠ H(B || A)`。证明格式必须通过索引、方向位，或一套无歧义的树遍历规则，告诉验证者每个兄弟应放在当前哈希的哪一侧。把一对哈希排序后再拼接虽然能让证明不再需要方向，却也把左右位置从承诺中删除，得到的是另一种数据结构和安全语义。

完整二叉树每向上一层，覆盖的叶子数量翻倍。N 个叶子的树高约为 log₂N，因此单个包含证明只需 O(log N) 个哈希，验证也执行 O(log N) 次哈希。根仍然只有一个固定长度的哈希值。构建整棵树或生成任意叶子的证明，则需要证明者保存或重新取得相应的中间节点；短证明并不意味着整棵树可以凭空恢复。

## 可执行示例把方向写进证明

同目录的 [完整 Node.js 示例](./merkle-proof.mjs)使用 `node:crypto` 实现上述四叶树。它把每个证明步骤表示为 `{ side, hash }`，验证器据此决定拼接顺序：

```js
function verify(value, proof, expectedRoot) {
    let current = leafHash(value);

    for (const step of proof) {
        current = step.side === "left" ? nodeHash(step.hash, current) : nodeHash(current, step.hash);
    }

    return current.equals(expectedRoot);
}
```

该示例在 Node.js 24.21.0 上执行：

```sh
node merkle-proof.mjs
```

关键输出为：

```text
root=42fc54eeb6352f90cc81fdd5791292cca3974a168208b395b06a76240b24884d
gamma=true
Gamma=false
```

只把 `gamma` 改成 `Gamma` 就会产生不同的叶子哈希，原证明无法重建同一个根。类似地，调换任一步的 `side`，或修改任何一个兄弟哈希，也会使验证失败。

示例故意只处理四个叶子，用来保持路径清楚。真实协议必须定义任意叶子数的树形，不能由实现者自行决定奇数节点是提升、复制还是与其他节点合并。RFC 9162 对 n 个输入采用递归分割：取小于 n 的最大二次幂 k，左子树处理前 k 个输入，右子树处理剩余输入。七个叶子因此分成四个和三个，而不是简单复制最后一个叶子。

[RFC 9162 的包含证明算法](https://www.rfc-editor.org/rfc/rfc9162.html#section-2.1.3)还把 `leaf_index` 和 `tree_size` 纳入验证。它们共同决定非完整树中的路径与方向，并用于拒绝越界索引、路径过短和路径过长。若协议只传一串兄弟哈希而不固定树大小和索引，同一串材料可能无法唯一说明它承诺的是哪棵树、哪个位置。

## 根匹配证明了什么

包含证明成立，只说明：在所选哈希函数、字节编码、树形规则和目标根之下，这条记录位于所声明的位置。它不会自动证明以下事情：

- 根来自可信发布者，或根没有在传输途中被替换。
- 这棵树是最新版本，或发布者没有向不同观察者展示不同的根。
- 记录内容本身真实、合法，或由某个身份签名。
- 某个未提供的值不在树中。

因此，根必须通过额外的信任机制取得，例如受认证的通道、数字签名或已经达成共识的账本状态。若要证明日志只能追加，还需要比较两个树快照的 **consistency proof**；RFC 9162 将它与单叶子的 inclusion proof 分开定义。若要证明“不存在”，普通 Merkle tree 也不够，通常需要把键空间、排序规则和相邻关系纳入结构。

实现协议时，还应把记录的字节编码写进规范。字符串采用 UTF-8 还是其他编码，整数采用何种字节序，对象字段如何排序，是否保留空白，都会改变叶子哈希。双方“看见相同内容”不代表实际哈希输入相同。先完成确定性序列化，再执行域分离哈希，证明才具有可互操作的含义。

Merkle 包含证明的价值不是让一个哈希替代全部信任，而是把验证范围压缩到一条路径：可信根固定了整个有序快照，兄弟哈希补齐目标叶子到根之间缺失的结构。只要树的构造、位置和编码都被明确约定，验证者就能用对数规模的材料检查局部成员关系，同时保留对整批数据的承诺。
