# 写作指南

本指南说明博客的选题范围、文章组织和交付格式，适用于文章新增与修订，以及定时和手动写作任务。准确、完整、连贯、易读是基本要求；在此基础上减少重复和无关内容，保留理解问题所需的技术深度。

## 选题与读者

博客覆盖计算机相关的所有知识领域，包括计算理论与数学基础、算法与数据结构、体系结构与硬件、操作系统、网络、编程语言与编译、软件开发与工程实践、数据库与数据处理、人工智能、安全、图形与多媒体、人机交互及相关应用。这些方向用于说明范围，不构成选题白名单，也不要求按固定比例轮换。

每篇文章选择一个清楚的学习目标：解释概念或机制、推导原理、分析实现、解决实际问题、比较方案，或者介绍有价值的技术进展。可以写基础知识，也可以深入专项研究；以读者能理解什么、判断什么或完成什么决定范围，不要求一篇文章覆盖整个领域，也不强行把所有主题改写成工程故障。候选主题从开放的计算机知识范围中选择，已有文章用于随后查重，不是选题池，也不决定以后只能写哪些领域。

按主题说明必要的前置知识，不能默认每位读者都熟悉某门语言或某个技术栈。正文默认使用简体中文，标准术语、API 和标识符保留准确写法。

## 新增与修订的判断

先形成候选主题，再按核心概念、API、常见中英文名称和同义词在 `articles/` 中定向检索。先读命中文章的元数据与相关段落，存在重合可能时再读全文，比较具体问题、适用版本与条件、主要结论及示例材料。不要求每次全量读取标题、标签、摘要或固定时间段的正文；命中过宽、过窄或发现遗漏线索时再调整关键词、扩大检查。

目录名只保证路径唯一，不能证明文章内容独立。是否新增按实际内容判断：

- 修正错误、补充同一问题或解释基本相同的机制、结论与示例时，优先修订已有文章，保留其目录和发表日期。
- 新场景、新机制、适用条件或版本变化带来独立的学习价值时，可以另写一篇。相关引用应服务于当前主题的理解。
- 多篇文章可以共用前置知识、领域和标签，不要求主题互斥。无新增价值的重复稿不能靠改标题、换目录名或增加序号、日期变成新文章。

目录已被占用但文章确实不同的，选用能准确区分问题的主题限定词。检索结果只支持已检查范围内的判断，不声称绝对没有重复。站点允许同日发表多篇不同文章；定时、手动新增及其重试如何区分执行，见[任务定义](../automation/daily-blog.md#开始与恢复)。

## 文章目录与元数据

每篇文章独立放在 `articles/<slug>/` 中。`slug` 是简短、明确的英文主题名称，目录内共同维护正文与配图、附件，例如：

```text
articles/volatile-increment/
├─ index.md
├─ images/
│  └─ increment-interleaving.png
└─ IncrementDemo.java
```

`index.md` 是正文，图片和附件按需添加。正文以 YAML 元数据开头：

```md
---
title: 为什么 volatile 不能保证自增原子性
date: 2026-09-07
domain: Java
tags: [Java, Concurrency, Volatile]
---

两个线程同时对同一个 volatile 变量执行自增，结果仍可能丢失更新。问题出在读取、计算和写回之间的交错。

## 可见性并不合并三个操作

如果两个线程都读到 0，各自计算出 1 再写回，最终结果就是 1。
```

- `title`、`date`、`domain` 和字符串数组 `tags` 必填，标签不带 `#`；不在元数据中重复填写 `id`。
- 目录名是文章的唯一标识，使用小写英文、数字和连字符，突出主题或标准技术名称，不添加日期和无关前缀。公开地址直接使用 `/<slug>/`，例如 `/volatile-increment/`。`date` 记录首次发表日期，允许多篇文章相同。
- 目录名不能与现有文章重名或占用站点保留路径，完整限制由[文章契约](../scripts/content/article.ts)校验。
- `domain` 表达文章的主要领域，`tags` 补充具体概念。优先选用[领域分组](../scripts/content/domains.ts)中准确的细分名称，遇到尚未列入的新方向仍可增加合适名称；页面会显示这些领域，不把分类表当成选题白名单。分组只在该文件维护，不另存一份文章索引。
- 首次发表不填 `updated`；修订保留原日期和目录名，以 `updated` 记录实际修订日期。修改标题不改变文章地址。
- 正文标题从二级开始，文章标题由页面模板生成。数学公式在构建时转为 MathML。

作者本人的署名、示例包名和个人标识使用 `allurx`，Java 示例命名空间使用 `io.allurx`；保留他人署名和版权信息。

## 组织与表达

### 固定必需信息，按主题选择结构

先确定读者要理解、判断或完成什么，再列出大纲。每篇文章都应让读者找到以下信息；相关信息可自然写入开篇、正文和示例，不要求分别设置同名章节：

- **学习目标与前提**：讨论什么、为什么有用，需要哪些已有知识，以及影响结论的适用范围。
- **技术主线**：按理解或操作顺序介绍概念、机制、步骤和因果关系，说明每一节如何推进目标。
- **依据与观察**：为关键判断提供规范、源码、推导或实验依据；有示例时交代环境、输入、观察点及结果含义。
- **结论与边界**：回答开篇的问题，说明结论成立的条件、重要限制和必要取舍；需要读者行动时给出可执行的下一步。

纯概念或数学推导不必增加运行环境和实验；简短文章可在几个连贯段落中完成上述信息。已有解释充分时，不重复增加摘要、总结、检查表或与主题无关的章节。

### 按文章用途安排阅读顺序

以下是常见组织方式，用来规划信息顺序，不是固定标题模板，也不限制文章类型。混合用途的文章先确定一条主线，再在相关位置补充其他内容。

| 主要用途 | 建议的推进顺序 |
| --- | --- |
| 原理解释与推导 | 提出问题与假设，建立概念或模型，逐步推导，用例子解释结论，再讨论边界 |
| 教程与操作指南 | 说明目标结果和准备条件，按实际操作顺序展开，在关键步骤验证结果，再处理必要的失败与限制 |
| 故障分析 | 明确现象与复现条件，取得证据，解释原因，对照修复方案及结果，说明适用边界 |
| 源码分析 | 说明版本和要解释的行为，建立职责与调用关系，沿关键路径分析状态和分支，用行为或例子收束结论 |
| 方案比较 | 明确场景、约束与比较指标，按相同条件比较行为和代价，再给出推荐与选择条件 |
| 概念或 API 参考 | 先给定义与适用范围，再按读者查找方式组织契约、参数或分类，配必要例子和限制 |

章节按主线取舍、合并或拆分，不以固定章节数量、字数或研究强度衡量质量。术语在首次影响推理时就地说明；切换版本、运行环境或规范与实现的讨论范围时，先交代变化。

这些组织原则参考 [Google Technical Writing 的文档组织方法](https://developers.google.com/tech-writing/two/large-docs)和 [Diátaxis 对读者需求与文档用途的区分](https://diataxis.fr/)。本文采用的是按读者目标安排信息的原则，不要求博客机械套用其分类或章节。

### 标题、段落与代码衔接

小标题应表达本节推进的具体问题，段落使用完整、连贯的句子，避免标签、术语堆叠和残句。建议与边界要说明它们如何从前文机制得出，不在结尾堆列无关知识点，也不在开篇、各节与结尾反复复述同一结论。

源码和长示例前先说明其职责、入口和本节关注的状态或分支，代码后解释观察与结论的关系。按实际调用链或推导拆解，不让读者先阅读整段实现再自行拼接原因；完整代码较长时可放同目录附件，正文保留理解主线需要的片段。必要的技术深度、契约和反例不能因整理结构而删去。

正文只包含读者理解主题所需的内容。操作记录、提交回执和内部检查表作为任务辅助资料单独保存；必要的实验条件和结果用于解释技术结论。

修订和重构以文章整体的准确性、完整性和阅读目标为准。原文是待核验的输入，核实后保留有用内容，纠正或替换错误，删减无关重复，补齐读者需要但原文未提供的概念、推理、示例、证据和资料；不以原有章节、篇幅或资源数量限制必要调整。同时更新受影响的代码块内注释、输出、图示和结论，检查同一判断在全文中的所有出现位置，形成可独立阅读的成稿。

## 来源与示例

### 语言与资料选择

示例首先选择最能解释当前问题的语言、工具或数学表达。多种语言同样合适时，优先使用作者熟悉的 Java、TypeScript 或 JavaScript，便于核验和维护。这一偏好不限制选题范围；主题依赖其他语言或平台时，使用对应的语言和工具。

Java 适合 JVM、Java 并发和 Java 生态；TypeScript 适合前端工程、类型建模和需要静态类型约束的 Web 示例；JavaScript 适合其运行机制、浏览器原生 API 和可直接在控制台运行的短例子。通用算法和机制也按解释效果选择，不为同时展示多种语言重复实现同一示例。

易变技术事实核对适用的官方原始资料，在对应结论处链接来源，区分规范保证、实现细节与推导。原理论证、研究结果和历史事实优先引用规范、论文、原始材料或维护者资料。版本、实现和运行环境须与实际分析的代码、材料及结论一致。

### 版本与运行环境

技术示例应说明适用版本和必要环境，覆盖影响行为的运行时、编译器、框架、数据库、依赖及工具组合。同篇示例可统一交代基线；局部使用不同版本时就地说明，不要求每个代码块重复一遍。涉及具体实现或工具链行为时，协议或标准版本不能代替相应版本；功能引入版本、兼容下限与本文选定的示例基线分别说明。

选择或重新调整通用示例基线时，有官方 LTS、Extended 等长期维护通道的，优先采用最新、适用且仍受支持的版本；没有这类通道的，采用受支持的稳定版本。核对主题需求、目标环境、依赖兼容性和实际可获得的维护渠道，不把商业支持默认当作公开维护，也不直接采用本机默认版本。记录影响复现的具体发行版、版本和配置，既有实验不能仅改版本号就声称完成升级验证。

历史源码、版本差异、新特性和已有系统的兼容性分析使用主题对应的版本，并交代选用原因和适用边界。跨版本引用资料、源码与运行结果时，说明各自支持哪个结论，不能用一个版本的运行结果替代另一个版本的验证。与运行无关的概念和数学推导只说明所需定义、假设或标准，不虚构软件环境。

声称实跑时，注明实际验证的完整版本及影响结果的操作系统、模块模式、编译选项或服务配置。未执行的内容明确为源码分析、结构片段或按契约推导的预期结果，并给出其目标环境；不能把最低支持版本、引用文档版本或计划使用的版本写成实测环境。

### 可复现示例与结果

代码前先说清要验证的机制、关键输入和观察点，再呈现相关实现；指标先解释含义，再用于比较。完整示例包含版本、必要的导入、依赖、入口、输入和执行命令，篇幅较长时可放同目录附件，正文保留理解主线所需的片段。

区分可独立执行的完整示例、需要接入已有应用的片段、源码摘录和伪代码。片段说明调用前提和省略部分，不为追求完整强行扩成无关项目；与主题无关的第三方依赖能用标准库清楚表达时，优先减少复现负担。

验证有明确预期的完整示例及本次修改涉及的失败场景，核对正文片段、附件、命令和结果的一致性。类型检查、静态页面构建通过不代表文章中的程序或外部服务已经验证。缺少执行环境时说明未验证范围，不编造输出或性能数字；量化结论提供可复现材料，并说明实验条件与限制。

## 配图与附件

先判断资料要帮助读者理解或完成什么，再选择表达形式。能用清楚的正文说明时不额外制作资源；同一信息不在正文、图表和附件中重复堆放。

| 读者需要理解的内容 | 优先考虑的形式 |
| --- | --- |
| 概念、职责、状态或调用关系 | 清楚的文字配必要的结构图、流程图或时序图，原生矢量图优先使用 SVG |
| 参数、方案、输入输出和实验数据的比较 | Markdown 表格；数量或变化趋势不易从表中判断时使用图表，必要时附可复用的原始数据 |
| 数学关系与推导 | 逐步解释的公式，使用站点支持的 MathML 输出，避免将公式截图化 |
| 实际操作与界面状态 | 有明确顺序的步骤和真实截图；截图注明影响操作的产品版本，不生成伪造界面作为操作证据 |
| 可执行实现、配置或较长材料 | 正文保留讲解所需片段，完整源码或资料作为可直接使用的附件，并说明入口和使用方式 |

格式以准确、清晰、可访问、便于复现和维护为依据，不为统一扩展名转换已经合适的资源。截图使用能保留文字细节的位图，照片按清晰度和体积选择格式；图示和表格保留文字说明，确保无 JavaScript 阅读和打印时仍能理解。细节较多、缩小后难以辨认的图片提供原图链接，便于读者单独查看。新增格式先核对站点与目标浏览器的实际支持。

正文只引用实际交付且读者可访问的材料，不使用私有或临时文件地址。同目录材料使用相对链接，例如 `![两个线程的自增交错](./images/increment-interleaving.png)` 和 `[完整示例](./IncrementDemo.java)`。图片放在 `images/`，采用简短、描述内容的小写连字符文件名；代码附件遵循对应语言的命名要求。

引用其他文章时使用其公开路径，例如 `[volatile 自增](/volatile-increment/)`，不写源文件路径或固定域名。

**注意事项**：文章目录内的附件按包内相对路径公开，只放读者需要的文件。`index.html` 保留给生成页面，`index.md` 不复制到发布目录；每份资源只维护一个公开路径，不建立并行副本或重定向。

交付前逐项打开、渲染或执行与其类型对应的必要检查。图片核对可读性、裁切、标注和与正文的关系；代码与配置核对入口、版本、命令和输出；数据与文档核对内容、单位、来源和使用方法。文件存在或 HTTP 200 只能证明可取得，不能证明内容正确。修订正文后同步检查相关资源，保留准确的第三方署名和许可。

## 完成前检查

从头审阅正文，检查开篇承诺是否由主线兑现，读者能否沿概念、步骤、因果与示例理解结论；章节和段落顺序应服务当前文章用途。确认版本前提、代码注释、运行命令、附件和结果互相一致，关键结论具有相应依据。格式检查通过不能替代内容审阅。

按[开发指南的验证与预览](development.md#验证与预览)检查文章页面、链接和附件。正文与必需附件一起保存、提交；发布方式见[发布指南](deployment.md)。
