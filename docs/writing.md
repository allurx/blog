# 写作指南

本指南说明博客的选题范围、文章组织和交付格式，适用于文章新增与修订，以及定时和手动写作任务。准确、完整、连贯、易读是基本要求；在此基础上减少重复和无关内容，保留理解问题所需的技术深度。

## 选题与读者

博客覆盖计算机相关的所有知识领域，包括计算理论与数学基础、算法与数据结构、体系结构与硬件、操作系统、网络、编程语言与编译、软件开发与工程实践、数据库与数据处理、人工智能、安全、图形与多媒体、人机交互及相关应用。这些方向用于说明范围，不构成选题白名单，也不要求按固定比例轮换。

每篇文章选择一个清楚的学习目标：解释概念或机制、推导原理、分析实现、解决实际问题、比较方案，或者介绍有价值的技术进展。可以写基础知识，也可以深入专项研究；以读者能理解什么、判断什么或完成什么决定范围，不要求一篇文章覆盖整个领域，也不强行把所有主题改写成工程故障。候选主题从开放的计算机知识范围中选择，已有文章用于随后查重，不是选题池，也不决定以后只能写哪些领域。

按主题说明必要的前置知识，不能默认每位读者都熟悉某门语言或某个技术栈。示例选择最能解释当前问题的语言、工具或数学表达，不固定优先 Java 或 TypeScript。正文默认使用简体中文，标准术语、API 和标识符保留准确写法。

## 新增与修订的判断

先形成候选主题，再按核心概念、API、常见中英文名称和同义词在 `articles/` 中定向检索。先读命中文章的元数据与相关段落，存在重合可能时再读全文，比较具体问题、适用版本与条件、主要结论及示例材料。不要求每次全量读取标题、标签、摘要或固定时间段的正文；命中过宽、过窄或发现遗漏线索时再调整关键词、扩大检查。

目录名只保证路径唯一，不能证明文章内容独立。是否新增按实际内容判断：

- 修正错误、补充同一问题或解释基本相同的机制、结论与示例时，优先修订已有文章，保留其目录和发表日期。
- 新场景、新机制、适用条件或版本变化带来独立的学习价值时，可以另写一篇。相关引用应服务于当前主题的理解。
- 多篇文章可以共用前置知识、领域和标签，不要求主题互斥。无新增价值的重复稿不能靠改标题、换目录名或增加序号、日期变成新文章。

目录已被占用但文章确实不同的，选用能准确区分问题的主题限定词。检索结果只支持已检查范围内的判断，不声称绝对没有重复。站点允许同日发表多篇不同文章；定时、手动新增及其重试如何区分执行，见[任务定义](../automation/daily-blog.md#开始与恢复)。

## 文章目录与元数据

每篇文章独立放在 `articles/<slug>/` 中。`slug` 是简短、明确的英文主题名称，目录内共同维护正文与配图、附件，例如：

```text
articles/volatile-increment/
├─ index.md
├─ images/
│  └─ increment-interleaving.png
└─ IncrementDemo.java
```

`index.md` 是正文，图片和附件按需添加。正文以 YAML 元数据开头：

```md
---
title: 为什么 volatile 不能保证自增原子性
date: 2026-09-07
domain: Java
tags: [Java, Concurrency, Volatile]
---

两个线程同时对同一个 volatile 变量执行自增，结果仍可能丢失更新。问题出在读取、计算和写回之间的交错。

## 可见性并不合并三个操作

如果两个线程都读到 0，各自计算出 1 再写回，最终结果就是 1。
```

- `title`、`date`、`domain` 和字符串数组 `tags` 必填，标签不带 `#`；不在元数据中重复填写 `id`。
- 目录名是文章的唯一标识，使用小写英文、数字和连字符，突出主题或标准技术名称，不添加日期和无关前缀。公开地址直接使用 `/<slug>/`，例如 `/volatile-increment/`。`date` 记录首次发表日期，允许多篇文章相同。
- 目录名不能与现有文章重名或占用站点保留路径，完整限制由[文章契约](../scripts/content/article.ts)校验。
- `domain` 表达文章的主要领域，`tags` 补充具体概念。优先选用[领域分组](../scripts/content/domains.ts)中准确的细分名称，遇到尚未列入的新方向仍可增加合适名称；页面会显示这些领域，不把分类表当成选题白名单。分组只在该文件维护，不另存一份文章索引。
- 首次发表不填 `updated`；修订保留原日期和目录名，以 `updated` 记录实际修订日期。修改标题不改变文章地址。
- 正文标题从二级开始，文章标题由页面模板生成。数学公式在构建时转为 MathML。

作者本人的署名、示例包名和个人标识使用 `allurx`，Java 示例命名空间使用 `io.allurx`；保留他人署名和版权信息。

## 组织与表达

开篇交代文章讨论什么、为什么值得理解，以及影响结论的适用前提。章节按学习目标所需的概念和因果关系组织，让读者知道当前解释解决了什么、下一步为什么需要继续讨论。术语在首次影响推理时就地说明；切换版本、运行环境或规范与实现的讨论范围时，先交代变化。不用缩短篇幅代替解释，也不套固定章节、字数或研究强度。

小标题应表达本节推进的具体问题，段落使用完整、连贯的句子，避免标签、术语堆叠和残句。建议与边界要说明它们如何从前文机制得出，不在结尾堆列无关知识点，也不在开篇、各节与结尾反复复述同一结论。

正文只包含读者理解主题所需的内容。操作记录、提交回执和内部检查表作为任务辅助资料单独保存；必要的实验条件和结果用于解释技术结论。

修订直接形成自洽、完整、正确的成稿，同时更新受影响的推导、示例和结论。文章应能独立阅读。

## 来源与示例

易变技术事实核对适用的官方原始资料，在对应结论处链接来源，区分规范保证、实现细节与推导。原理论证、研究结果和历史事实优先引用规范、论文、原始材料或维护者资料。版本、实现和运行环境须与实际分析的代码、材料及结论一致。

代码前先说清要验证的机制、关键输入和观察点，再呈现相关实现；指标先解释含义，再用于比较。完整示例包含版本、必要的导入、依赖、入口、输入和执行命令，篇幅较长时可放同目录附件，正文保留理解主线所需的片段。

未执行的示例不称验证通过，不编造输出或性能数字。量化结论提供可复现材料，并说明执行环境与限制。

## 配图与附件

正文只引用实际交付且读者可访问的材料，不使用私有或临时文件地址。同目录材料使用相对链接，例如 `![两个线程的自增交错](./images/increment-interleaving.png)` 和 `[完整示例](./IncrementDemo.java)`。图片放在 `images/`，采用简短、描述内容的小写连字符文件名；代码附件遵循对应语言的命名要求。

引用其他文章时使用其公开路径，例如 `[volatile 自增](/volatile-increment/)`，不写源文件路径或固定域名。

**注意事项**：文章目录内的附件按包内相对路径公开，只放读者需要的文件。`index.html` 保留给生成页面，`index.md` 不复制到发布目录；每份资源只维护一个公开路径，不建立并行副本或重定向。

## 完成前检查

从头审阅正文，检查读者能否沿着概念、因果与示例理解推导，确认结论具有相应依据。格式检查通过不能替代内容审阅。

按[开发指南的验证与预览](development.md#验证与预览)检查文章页面、链接和附件。正文与必需附件一起保存、提交；发布方式见[发布指南](deployment.md)。
